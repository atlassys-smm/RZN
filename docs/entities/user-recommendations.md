# Рекомендации пользователя

Общий профиль принадлежит User, включая гостя, и предназначен для источников разных модулей. ПрофСтарт добавляет один неизменяемый источник на завершённый тип, включая дополнительные типы CMS. Каждый источник содержит показатели групп и профессий; в итоговом рейтинге участвуют только пары source_module/source_code с положительным весом в SOURCE_WEIGHTS. Итоговый рейтинг рассчитывается при каждом запросе из снимков источников и не сохраняется в БД. История отдельных тестов не меняется.

## UserRecommendation

Таблица `user_recommendations`. Уникальность user_id: один профиль на пользователя.

| Поле | Тип | Описание |
|---|---|---|
| `id` | bigint | PK |
| `user_id` | bigint | Уникальный FK → users.id |
| `created_at` | timestamp UTC | Создание профиля |
| `updated_at` | timestamp UTC | Последнее добавление или обновление источника |

## UserRecommendationSource

Таблица `user_recommendation_sources`. Уникальность (recommendation_id, source_module, source_code). Индекс (source_module, source_code) поддерживает выборку по модулю и коду. Источники ПрофСтарта неизменяемы после успешного завершения. Источники просмотров и ответов викторины обновляются сервером; API записи для клиента отсутствует.

| Поле | Тип | Описание |
|---|---|---|
| `id` | bigint | PK |
| `recommendation_id` | bigint | FK → user_recommendations.id |
| `source_module` | string | Модуль источника: profstart, professions или quiz |
| `source_code` | string | Код внутри модуля: solomin, holland, dellinger, views или answers |
| `source_reference` | jsonb | ПрофСтарт: ссылка на результат; views: window_start, window_end; quiz: last_session_id |
| `group_scores` | jsonb | ПрофСтарт: все показатели групп; views: profession_id/views_count; quiz: profession_id/answers_count |
| `profession_scores` | jsonb | Полный снимок соответствия профессиям: profession_id/name, score, position, reasons с группами и их баллами |
| `created_at` | timestamp UTC | Создание источника |
| `updated_at` | timestamp UTC | Последнее обновление; для views — исключающая верхняя граница учтённых событий |

Внутри JSON десятичные значения сохраняются строками для точности. Типизированные поля score, weight и contribution API возвращает числами; структура reasons зависит от поставщика источника. Завершённая сессия ПрофСтарта любого типа ссылается на источник уникальным recommendation_source_id; для in_progress и abandoned ссылка равна null. Связи group_id и profession_id внутри JSON — снимки, а не внешние ключи; сервис проверяет их при создании. Основные коды групп защищены.

Для источника ПрофСтарта учитываются все группы с положительным вкладом, включая неведущие. Изменения связей профессий и подписей групп в CMS не меняют сохранённые снимки.

## Итоговый рейтинг

Веса источников заданы в `app/models/user_recommendations/weights.py`: ("profstart", "solomin")=40, ("profstart", "holland")=40, ("profstart", "dellinger")=15, ("professions", "views")=4, ("quiz", "answers")=1. Веса относительные: при наличии всех пяти источников их сумма равна 100. В таблицах они не хранятся; CMS их не изменяет. Для новых поставщиков нужно добавить пару модуля и кода и её вес в SOURCE_WEIGHTS. Неизвестная пара имеет нулевое влияние.

GET рассчитывает максимум три профессии, не записывая результат. Рейтинг сортируется по score DESC, profession_id ASC. Возвращаются только положительные округлённые баллы существующих профессий; набор может быть короче трёх или пустым. При неполном наборе веса нормируются по имеющимся источникам с положительным весом. Источник без данной профессии участвует с нулевым вкладом. Источник с весом 0 сохраняется, но не влияет на выдачу. Округление — Decimal ROUND_HALF_UP до двух знаков после суммирования точных взвешенных вкладов.

[API](../api/user-recommendations.md) · [Расчёт ПрофСтарта](../subsystems/profstart/results.md).

## Описание профессии в итоговом ответе

Каждый элемент `professions` в `/users/me/recommendations` содержит `description`: текущее описание профессии из справочника или `null`. Оно читается при запросе, включая мягко удалённые профессии, и не сохраняется в `profession_scores` источника. Название, баллы, позиции и вклады продолжают формироваться из сохранённых результатов. Предпросмотр конструктора использует тот же сервис и формат ответа.

## Организации и направления в итоговом ответе

По максимум трём профессиям из итогового рейтинга рассчитываются три отдельных списка: `employers` (до 5 работодателей типа 1), `educations` (до 5 учебных заведений типа 2) и `education_programs` (до 5 направлений подготовки). Работодатели определяются через profession_employers, учебные заведения — через profession_education_programs → education_programs → organization_education_programs → organizations. Направления подбираются непосредственно через profession_education_programs → education_programs, независимо от наличия организаций. В каждом списке сначала идут записи с большим числом различных совпавших профессий, затем с меньшим ID. Несколько программ одной профессии не увеличивают её вклад в рейтинг организации. Элементы списков организаций содержат `organization` (полные данные организации), `profession_ids` (по возрастанию ID), `profession_count` и `position` (1–5). В списке направлений вместо `organization` возвращается `education_program`: id, name, education_level, duration, base_class, created_at, updated_at; остальные поля совпадают. Общее направление возвращается один раз независимо от числа его организаций. Профессии, связи, программы и организации с deleted_at участвуют в расчёте для сохранённых рекомендаций. Данные и связи читаются в текущем состоянии при каждом GET; снимки этих трёх списков не сохраняются. При отсутствии профессий или соответствующих связей массивы пустые; до создания профиля ответ остаётся null.

### Покрытие выбранных профессий

Правило покрытия применяется отдельно к каждому из трёх списков: employers, educations, education_programs. Сначала формируется топ-5 по числу различных совпавших профессий DESC и ID организации или направления ASC. Затем проверяется покрытие каждой выбранной профессии. Если для неё есть связанные записи, но ни одна не попала в топ-5, лучшая из них заменяет последнюю запись, удаление которой не лишает покрытия другие профессии. Одна запись может покрывать несколько профессий. После замен сохраняется сортировка по рейтингу; лимит — 5 уникальных записей в каждом списке. Если соответствующих связей нет, покрытие этой профессии в данном списке не требуется.

Правило действует для `/users/me/recommendations` и `/organizations/recommendations`, в том числе для профессий, связей, программ и организаций с `deleted_at`.

В каждой профессии возвращается `file`: собственный файл, а при пустом media_id — male_photo_file_id её шаблона аватара; если файлов нет, null. Правило совпадает с карточкой профессии. Данные файла читаются при GET, в снимки источников не записываются.

## Источник просмотров профессий

Пара источника — `source_module=professions`, `source_code=views`.
Он обновляется при GET рекомендаций и предпросмотре конструктора, если записи ещё
нет либо с её `updated_at` прошло строго больше 6 часов. Ровно через 6 часов
используется сохранённый результат. Счётчики не обновляются при каждом просмотре.

Первый запрос получает события из `analytics.profession_views` за интервал
`[время начала выборки − 30 суток, время начала выборки)`. Последующие запросы
получают `[предыдущее updated_at, время начала новой выборки)` и прибавляют
количество к сохранённым счётчикам. Это накопительная история после начальных
30 суток, а не скользящее окно. Считаются события просмотров, а не разные дни;
повторные строки одного события исключены представлением ClickHouse по ID.
Фильтрация выполняется по `occurred_at` и текущему `user_id`, границы — UTC
с точностью до миллисекунд. Запоздавшее событие с occurred_at до уже сохранённой
границы не попадает в последующую выборку; доставка аналитики остаётся best effort.

В `group_scores` хранятся только накопленные количества:

```json
[{"profession_id":42,"views_count":3},{"profession_id":73,"views_count":6}]
```

В `profession_scores` — все существующие профессии из счётчиков, их названия,
позиции и оценки `100 × views_count / max(views_count)` с ROUND_HALF_UP до двух
знаков. Для примера выше оценки равны 50 и 100. `reasons` содержит `views_count`
и `max_views_count`. При изменении максимума пересчитываются все оценки.
Счётчики неизвестных справочнику ID сохраняются, но такие профессии не выдаются.

`source_reference` содержит `window_start` начальной выборки, `window_end`
последней успешной выборки. `updated_at` совпадает
с `window_end`, а не с временем завершения HTTP-запроса. Счётчики, оценки и обе
даты источника/профиля обновляются одной транзакцией. Блокировка пользователя
с повторной проверкой срока исключает двойное прибавление при конкуренции.

Пустая успешная выборка тоже сохраняет дату обновления. Пустой источник views
не влияет на знаменатель рейтинга и полноту; без других источников ответ остаётся
null. Источник необязательный и не включается в `missing_sources`; обязательность
остальных источников с положительным весом сохраняется. Если views — единственный
доступный источник, рекомендации доступны, но без обязательных тестов неполны.

Подключение и выполнение HTTP-запросов вынесены в `app/services/clickhouse/service.py`;
user_recommendations задаёт SQL, параметры выборки и преобразование строк в счётчики.
Чтение выполняется через `ANALYTICS_CLICKHOUSE_URL` с существующими
`CLICKHOUSE_READER_USER` и `CLICKHOUSE_READER_PASSWORD`. При выключенной аналитике
или ошибке чтения сохранённые счётчики и updated_at не меняются; при отсутствии
снимка используются остальные источники. Рабочие события в PostgreSQL не копируются.


## Источник ответов викторины

Источник `quiz/answers` имеет относительный вес 1; вес `professions/views` — 4,
ПрофСтарт — 40/40/15. Он необязателен для `is_complete` и не входит в
`missing_sources`. Пустой источник не участвует в знаменателе рейтинга.

В `game_questions.profession_id` задаётся необязательная привязка к одной активной
профессии. При создании вопросов сессии, включая дополнительный финальный раунд,
привязка копируется в `game_session_questions.profession_id`. Существующие записи
миграция оставляет без привязки, исторические ответы автоматически не импортируются.

При раскрытии вопроса каждый собственный правильный ответ пользователя, включая
гостя и рядового участника команды, добавляет 1 профессии в счётчик Redis данной
сессии. Неправильные, пропущенные и непривязанные ответы не учитываются. Текстовые
типы case_study, prediction, argumentation, final_case исключены: игровой сервис
принимает их без содержательной проверки. Ответ капитана не переносится другим
участникам. Скорость, игровые очки, штрафы и бонусы не используются.

Redis хранит накопленные количества по паре user_id/profession_id и набор уже
учтённых пар session_question_id/participant_id. Отметка и инкремент выполняются
атомарно. Повторная оценка не увеличивает количество; повтор того же вопроса в
другой записи сессии или новой сессии учитывается отдельно.

При `finish` после раскрытия последнего вопроса последнего раунда накопленные
количества прибавляются к `group_scores`:
`[{"profession_id":42,"answers_count":3}]`. При досрочном finish количества
не начисляются. Другие сессии продолжают увеличивать те же счётчики без окна по времени.

Все `profession_scores` пересчитываются по формуле
`100 × answers_count / max(answers_count)`, ROUND_HALF_UP до двух знаков.
В `reasons` хранятся answers_count и max_answers_count. `source_reference`
содержит last_session_id; updated_at источника и профиля
обновляются при начислении. Состояние сессии и источники всех участников
фиксируются одной транзакцией PostgreSQL. Блокировка сессии и проверка FINISHED
исключают повторное начисление, блокировки пользователей — потерю параллельных
пополнений. Redis очищается после commit; при ошибке сохранения счётчики остаются
для повтора. Потерянное состояние Redis не восстанавливается из аналитики.
