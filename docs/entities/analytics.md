# Аналитика

## AnalyticsEvent

Бэкенд создаёт события, отправитель сохраняет их в общей таблице ClickHouse
`analytics.events`. Сейчас подключены индивидуальная и командная викторины,
а также жизненный цикл, ответы и результаты ПрофСтарт и обратная связь.
Сервисы вызывают `app.services.analytics.emit_event`; HTTP API приёма событий
от внешних устройств пока не реализован.

### Атрибуты

| Поле | Тип ClickHouse | Описание |
|---|---|---|
| `id` | UUID | Уникальный ID конкретного факта; сохраняется при повторах |
| `event_id` | UInt16 | Действие из `EventType(IntEnum)` |
| `module_id` | UInt8 | Функциональный модуль из `ModuleType(IntEnum)` |
| `device_id` | Nullable(Int64) | Конкретное устройство |
| `user_id` | Nullable(Int64) | Пользователь действия, если известен |
| `is_guest` | Nullable(Bool) | Снимок статуса пользователя в момент события: true — гость, false — OAuth, NULL — неизвестен или нет user_id |
| `session_id` | Nullable(Int64) | ID сессии соответствующего модуля |
| `occurred_at` | DateTime64(3, UTC) | Время действия |
| `received_at` | DateTime64(3, UTC) | Назначается ClickHouse при вставке |
| `payload` | String | JSON с параметрами конкретного события |

В Python payload передаётся словарём. Enum проверяются и сериализуются в числа
до помещения в очередь. ORM-объекты и AsyncSession в очередь не передаются.
Коды и названия перечислены в [типах событий](../references/analytics-event-types.md)
и [источниках событий](../references/event-sources.md). После публикации коды
не перенумеровываются и не назначаются другому значению.

`device_id` равен NULL, если конкретное устройство неизвестно. Тип оборудования
и программный комплекс в событии не хранятся; модуль задаётся `module_id`.

Сессия различается по `(module_id, session_id)`. Числовые ID сессий
внутри одного модуля не должны переиспользоваться, пока соответствующие события
остаются в ClickHouse.

`is_guest` передаётся отдельным аргументом `emit_event`, а не внутри payload.
Значение считывается из `users.is_guest` при выполнении бизнес-операции до commit;
в очередь после commit попадает обычный bool или None. Статус старого события
не меняется при последующем OAuth-входе. Для события без конкретного `user_id`
отправитель сохраняет NULL независимо от переданного признака.
У общей игры `is_guest=NULL`; в `payload.participants[]` стартового события
сохраняется снимок `is_guest` каждого участника. Персональная регистрация
и оценённый ответ викторины содержат признак на верхнем уровне события.
ПрофСтарт передаёт его для старта, ответа, окончания, прерывания и каждой
рекомендации; анкеты — для старта, оценок и окончания.

### Хранение и доставка

Таблица использует `ReplacingMergeTree(received_at)`, ключ
`(module_id, id)` и месячную партицию `toYYYYMM(occurred_at)`.
Представления читают `analytics.events_unique` с FINAL и учитывают повтор факта
один раз. DDL находится в `infra/clickhouse/migrations`; запуск:
`docker compose exec api python infra/clickhouse/scripts/update.py`.

`emit_event` выполняет только локальную постановку и не ждёт сеть или свободное
место в очереди. Фоновый отправитель собирает пакеты, ждёт подтверждения записи
и повторяет неудачную доставку с тем же содержимым и токеном вставки.
UUID5 создаётся из модуля, сессии, действия и стабильного `event_key`.
при отсутствии ключа используется UUID4. Время действия не меняется при повторах.

Очередь ограничена количеством событий и байтами. Доставка best effort:
авария/reload, переполнение или исчерпание повторов могут терять события.
Отсутствующий факт не восстанавливается SQL-представлением.

### Викторина

`module_id=1` (QUIZ_IND) — индивидуальная
викторина, `module_id=2` (QUIZ_TEAM) — командная. Режим определяется модулем.
[Требуемые показатели](../interfaces/admin-portal/dashboards.md#индивидуальная-викторина).

| event_id | Действие | Payload |
|---|---|---|
| 1 | SESSION_STARTED | participant_count, team_count, participants[{participant_id,user_id,is_guest}], teams[{team_id,participant_count}]; для командной игры tracks_participant_answers=true |
| 2 | PARTICIPANT_JOINED | participant_id, team_id |
| 3 | ANSWER_EVALUATED | session_question_id, participant_id, team_id, is_correct |
| 4 | SESSION_FINISHED | duration_ms, finish_reason; для командной игры participants[{participant_id,team_id}] — состав на окончание |
| 6 | ANSWER_SUBMITTED | Только командная игра: session_question_id, participant_id, team_id — факт принятого личного ответа, без содержимого |

Личный ответ командной игры отправляется после commit через синхронную
постановку в очередь; `event_key=quiz_answer_submitted:<session_question_id>:<participant_id>`.
`user_id` и `is_guest` передаются на верхнем уровне для отправившего ответ.
Событие создаётся для обычного участника и капитана, независимо от раскрытия.
`tracks_participant_answers` в старте отделяет игры с полным новым сбором от
исторических. Доля личного участия использует только новые завершённые игры
и состав команд на окончание; [формулы и ограничения](../subsystems/analytics/dashboards/pak-detail/led-platform.md#правильность-и-личное-участие).

Количество участников и непустых команд фиксируется на старте. Повторное
подключение не создаёт регистрации. Ответ оценивается при раскрытии вопроса;
командный ответ учитывается один раз от команды. Неотвеченные вопросы не входят
в процент ошибок. Тексты, сложность, тип, варианты, ответы и баллы не отправляются.
Завершение определяется переходом сессии в `FINISHED` и записью `finished_at`
через `/finish`. Для этого события `finish_reason="completed"`: пропуски вопросов,
число обработанных ответов и позиция в игре на завершённость не влияют.
Без события окончания сессия не считается завершённой. Отдельный счётчик
обработанных вопросов для аналитики не ведётся.
`duration_ms` включает паузы, при неизвестном старте — null. Уникальные пользователи
считаются по ненулевым user_id, это не оценка числа людей без идентификации.

Представления: quiz_sessions, quiz_answers, quiz_teams, quiz_participants.
Соединения используют module_id и session_id. Признак completed
в quiz_sessions определяется наличием finished_at, а не значением finish_reason.
Период дашборда
выбирает игры по started_at; границы дат — Europe/Moscow.
Правильность — correct/evaluated; завершённость — completed/started.
Средняя длительность и её распределение — только completed с известным временем.
Нулевой знаменатель — null. Без окончания игра не объявляется автоматически прерванной.

### ПрофСтарт: события прохождения

`module_id=4`. Сервисы отправляют факты только после commit:

| event_id | Факт | Дополнительные данные |
|---|---|---|
| 1 | SESSION_STARTED | Версия теста, название и число вопросов |
| 6 | ANSWER_SUBMITTED | Вопрос, выбранный вариант, группа, вклад ответа и duration_ms от старта/предыдущего ответа |
| 4 | SESSION_FINISHED | Длительность, answered_count и сохранённый group_scores, включая нули |
| 9 | SESSION_ABANDONED | Явное прерывание, длительность и достигнутый прогресс |
| 5 | PROFESSION_RECOMMENDED | Одна профессия сохранённого результата |

Повтор принятого ответа и повтор прерывания не создают событий. Возраст и
возрастная группа пока не передаются; добавить их снимок на старте — TODO.
Миграция ClickHouse 0006 и 13 SQL-вопросов дашборда pak.profstart подключают
сессии, ответы, показатели групп и рекомендации к согласованным графикам.
[Полный контракт и согласованные расчёты](../subsystems/analytics/dashboards/pak-detail/profstart.md).

### ПрофСтарт: рекомендованные профессии

`event_id=5` (PROFESSION_RECOMMENDED), `module_id=4` (PROFSTART). После успешного commit последнего ответа
создаётся по одному событию на профессию из сохранённого результата теста.
Используется полный список рекомендаций этого теста, без ограничения
тремя профессиями общего профиля.

| Поле | Значение |
|---|---|
| `session_id` | ID прохождения TestSession; общий для всех профессий одного результата |
| `user_id` | Пользователь прохождения |
| `occurred_at` | Сохранённое время завершения теста completed_at |
| `device_id` | NULL: устройство в этом потоке не передаётся |
| `payload.test_id` | ID версии теста |
| `payload.test_type_id` | ID типа теста |
| `payload.test_code_type` | Код типа теста |
| `payload.test_version` | Номер версии теста |
| `payload.profession_id` | ID рекомендованной профессии |
| `payload.profession_name` | Название профессии на момент результата |
| `payload.score` | Числовой нормированный балл рекомендации |
| `payload.position` | Место профессии в результате, начиная с 1 |

`event_key=profstart_profession_recommended:<session_id>:<profession_id>`
задаёт стабильный UUID факта. Внутри одного результата профессии уже
объединены по profession_id, независимо от числа совпавших групп теста.
Пять профессий дают пять событий и один подбор: подборы считаются
по различным `(module_id, session_id)`, люди — по различным
ненулевым user_id, частота профессии — по результатам с этой профессией.
Все такие запросы используют `analytics.events_unique` и фильтр действия 5.

Незавершённый тест, ошибка транзакции и пустой список профессий не создают
событий рекомендации. Чтение результата и повтор последнего ответа
завершённого прохождения не создают новых фактов. Поле selection_size
не передаётся. По этим событиям нельзя получить число всех завершённых
тестов, включая результаты без профессий: для этого используется отдельный
факт SESSION_FINISHED=4 модуля PROFSTART. Доставка остаётся best effort; потеря части событий может
повлиять на рейтинг профессий. Исторические результаты не выгружаются.

В Metabase показатель «Для X человек подобраны профессии» подключён
в [Главный Dashboard → Вовлечённость](../subsystems/analytics/dashboards/general.md#вовлечённость).
Графики модуля подключены в pak.profstart через profstart_sessions,
profstart_answers, profstart_group_results и profstart_recommendations. Они
выбирают реальные старты и завершения; старые рекомендации без этих фактов
сохраняются, но не объявляются прохождениями.

### Обратная связь

`module_id=5`: реальный старт `SURVEY_STARTED=7`,
итоговые числовые ответы `ANSWER_SUBMITTED=6`, окончание `SURVEY_FINISHED=8`.
`session_id` — ID SurveyResponse. Метаданные анкеты и точки есть во всех событиях;
оценки содержат ID/текст/тип вопроса, rating и границы шкалы. Текстовые ответы
в ClickHouse не передаются. События создаются только после commit.
При старом запросе без response_id отправляются оценки и окончание без
вымышленного старта. История автоматически не выгружается.

Представления: `feedback_sessions`, `feedback_ratings`. Полный контракт,
совместимость и формулы — в [аналитике анкет](../subsystems/analytics/surveys.md).

Подключение и развёртывание: [ClickHouse и Metabase](../subsystems/analytics/clickhouse-metabase.md).

### Сводные сессии модулей

`analytics.module_sessions` (ClickHouse `0007_module_sessions.sql`) объединяет
жизненный цикл сценариев по `(module_id, session_id)`.
Это обычное представление над `events_unique`, без новой физической таблицы.

| Поле | Содержимое |
|---|---|
| module_id | Код модуля |
| module_name | Название модуля; для неизвестного кода — «Модуль #код» |
| session_id | ID сессии внутри модуля |
| device_id | Известный ID устройства, иначе NULL |
| started_at | Первый реальный старт (1, для анкет 7), иначе NULL |
| finished_at | Первое окончание (4, для анкет 8), иначе NULL |
| abandoned_at | Явное прерывание ПрофСтарт (9), иначе NULL |
| duration_ms | Длительность из события окончания, иначе NULL |
| has_start | Присутствует реальный старт |
| completed | Присутствует событие окончания; прерывание не считается окончанием |

Отчёты отбирают `has_start` и период по `started_at`. Один старт означает одно
взаимодействие, достижение цели — завершение сессии. Исторические окончания
без старта, ответы и рекомендации не увеличивают число взаимодействий.
Схема событий и отправка из сервисов не меняются.
[Правила и графики сводной аналитики](../subsystems/analytics/dashboards/paks-summary.md).

### Посещаемость

`analytics.visitor_activity` (ClickHouse 0008) представляет персональные события
с известным `user_id` и участников стартового снимка викторины. Поля: `id`,
`module_id`, `device_id`, `user_id`, `is_guest`, `occurred_at`.
Источником служит `events_unique`; повтор одной личности между событиями
и ПАК устраняется при расчёте уникальных посетителей, не по числу строк view.

Общий итог включает неизвестный статус. Категория пользователя определяется
последним известным `is_guest` внутри выбранного периода; NULL не стирает
известный снимок. При одинаковом времени false имеет приоритет над true.
Категории взаимоисключающие; их сумма может быть меньше итога из-за истории
без статуса. Динамика — независимые уникальные user_id по дням или неделям МСК,
не сумма уникальных дней. [Полные расчёты](../subsystems/analytics/dashboards/general.md#посещаемость).
