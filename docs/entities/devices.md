# Устройства

Описание сущности для регистрации физических устройств (LED-экранов), взаимодействующих с API от собственного имени.

---

## Device (Устройство)

Учётная запись LED-устройства. Регистрируется администратором через CMS перед вводом экрана в эксплуатацию. Позволяет нескольким LED-экранам работать параллельно и независимо друг от друга.

### Атрибуты

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | integer (int64, автоинкремент) | Уникальный идентификатор устройства (используется как `device_id`) |
| `name` | string | Название устройства (например, «LED-1 Холл») |
| `location` | string, nullable | Расположение устройства |
| `is_active` | boolean | Устройство активно. `false` — токен отозван, запросы отклоняются |
| `created_at` | timestamp | Дата регистрации |
| `revoked_at` | timestamp, nullable | Дата отзыва токена |

### Аутентификация

- При регистрации (`POST /cms/devices`) выдаётся долгоживущий JWT (`device token`) с `sub = device.id`. Токен показывается один раз и сохраняется в конфигурации LED-плеера.
- Каждый запрос от LED-экрана (получение состояния, запуск/остановка показа) сопровождается этим токеном — сервер проверяет подпись и то, что `is_active = true`.
- Отзыв токена (`DELETE /cms/devices/{id}`) переводит устройство в `is_active = false` — дальнейшие запросы с этим токеном отклоняются.
- Обновление токена (`POST /cms/devices/{id}/refresh-token`) выпускает новый токен и аннулирует старый для этого устройства.
- Несколько устройств могут иметь параллельно активные показы — сессии показа различаются по `device_id`.

### Уведомления о сессиях

Любое активное устройство независимо от ролей подключается к `/api/device/sessions/ws?token=<device_jwt>` до запуска сессии оператором. События `session_started` и `session_finished` содержат `payload` с `device_id`, `session_id` и `module` (`quiz` или `interactive_video`). Устройство получает только свои события; викторина сообщает о создании уже в статусе waiting. Формат и правила переподключения описаны в [WebSocket API](../api/websocket.md#сессии-устройства).

### Где используется

- **CMS** — регистрация и отзыв устройств
- **Профессии в действии** — привязка сессии показа (`InteractiveVideoSession`) к конкретному `device_id`


## DeviceRoleAssignment (Роли устройства)

Таблица `device_roles` хранит несколько ролей устройства. У пары `(device_id, role)` составной первичный ключ; повторное назначение одной роли исключено. FK ссылается на `devices.id` с каскадным удалением связей при физическом удалении устройства. Обычный DELETE устройства по-прежнему только отзывает его токен.

| Поле | Тип | Описание |
|------|-----|----------|
| `device_id` | integer (int64, FK, PK) | Устройство |
| `role` | integer enum, PK | 1 — викторина и профессии в действии; 2 — аватар; 3 — ПрофСтарт; 4 — обратная связь |

Роли читаются из БД при авторизации и не включаются в JWT. API устройства возвращает `roles` — отсортированный массив числовых кодов. При регистрации нужен как минимум один код, дубли и неизвестные значения возвращают 422. `PUT /api/cms/devices/{device_id}/roles` с телом `{"roles": [1, 3]}` целиком заменяет список; доступен admin/operator. Изменение действует сразу для прежнего токена.

Seed-миграция `0056` назначает существующим устройствам все четыре роли, сохраняя прежний доступ. Для новых устройств автоматических ролей нет.


## Временная привязка пользователя

QR-подключение хранится в Redis, без таблицы в PostgreSQL. Одно устройство связано с одним
User до часа; User JWT остаётся на телефоне. Маршруты `/api/device/auth/*`, сроки и правила
доступа описаны в [авторизации](../subsystems/auth-sessions.md#подключение-пользователя-к-устройству-через-qr).
