# Подсистема «Идентификация и регистрация»

Инфраструктурный auth-сервис. Встраивается во все точки взаимодействия: терминалы, мобильные устройства, сенсорные стойки, LED. Выдаёт токены, проверяет credentials, обслуживает OAuth 2.0 через внешних провайдеров. Не имеет собственного клиентского фасада — его используют все подсистемы.

---

## Единая модель пользователя

Пользователь платформы — **одна запись** в базе данных (`User`), которая может быть в гостевом или авторизованном состоянии:

- **Гость** — создан при первом сканировании QR-кода, имеет `is_guest = true` и `guest_expires_at`, без OAuth-данных
- **Авторизованный** — тот же пользователь, у которого `is_guest = false` и заполнены OAuth-данные

Результаты всех активностей (LED-сессии, ПрофСтарт, анкеты) всегда привязаны к `id` пользователя. При привязке новой OAuth-личности к действующему гостю перенос данных не требуется — сохраняется та же запись. Если аккаунт провайдера уже существует, вход выполняется в него, а история гостя остаётся отдельно.

---

## Способы авторизации

- **OAuth 2.0 через внешних провайдеров:**
  - Яндекс ID (имя, email, пол, дата рождения)
  - VK ID (имя, email, пол, дата рождения)
- **Гостевой режим** — без авторизации, по QR-коду, с возможностью последующей авторизации
- Локальная регистрация по ID/паролю **не поддерживается**

## Создание и авторизация пользователя

### Сценарий 1: Повторное сканирование QR (авторизованный пользователь)

1. Пользователь сканирует QR-код на терминале
2. Фронтенд отправляет access из памяти; после перезагрузки получает его через refresh-cookie
3. Сервер проверяет JWT, находит User по `sub` и действующую сессию по `sid`
4. Пользователь узнаётся — новая запись не создаётся, переход в активность или профиль

### Сценарий 2: Первый контакт — выбор OAuth

1. Пользователь сканирует QR-код на терминале
2. Если восстановить вход через refresh-cookie не удалось, фронтенд показывает экран выбора
3. Пользователь видит экран: **«Войти через OAuth или продолжить как гость?»** с чекбоксом согласия на ПДн
4. Пользователь ставит галочку согласия (обязательная, со ссылкой на текст)
5. Нажимает кнопку провайдера (Яндекс ID / VK ID)
6. Фронтенд запускает OAuth и проверяет state; версию согласия передаёт в API при завершении входа
7. Авторизация у провайдера, callback с кодом
8. Сервер обменивает код на данные пользователя
9. Создаётся `User` со `status = active`, заполняются OAuth-поля
10. Выдача JWT, переход в активность

### Сценарий 3: Первый контакт — выбор «Гость»

1. Пользователь сканирует QR-код на терминале
2. Если восстановить вход через refresh-cookie не удалось, фронтенд показывает экран выбора
3. Пользователь видит экран: **«Войти через OAuth или продолжить как гость?»** с чекбоксом согласия на ПДн
4. Пользователь ставит галочку согласия (обязательная)
5. Нажимает «Продолжить как гость»
6. Сервер записывает `ConsentAcceptance`, создаёт `User` со `status = active`, `is_guest = true`, `guest_expires_at` (24 часа)
7. Access JWT хранится в памяти фронтенда, refresh — в HttpOnly cookie; ID пользователя находится в claim `sub`
8. Все результаты привязываются к `id` пользователя

### Сценарий 4: Гость авторизуется позже

1. В личном кабинете гость видит баннер «Авторизуйтесь» с чекбоксом согласия
2. Пользователь ставит галочку, нажимает «Войти через OAuth»
3. Фронтенд сохраняет выбор версии согласия и запускает OAuth
4. Редирект на провайдера, авторизация, callback с кодом
5. Сервер проверяет действующего гостя по access, переданному фронтендом при завершении OAuth
6. Заполняются OAuth-поля, `is_guest` устанавливается в `false` (гость становится обычным авторизованным пользователем)
7. Запись согласия и выдача новой сессии, данные уже привязаны. Если OAuth-аккаунт уже существует, вход выполняется в него, история гостя остаётся отдельно

## Токены и сессии

Реализованный контракт и ограничения: [Авторизация и серверные сессии](auth-sessions.md). OAuth-сценарии реализованы; для внешнего входа нужно настроить приложения и точные Redirect URI у провайдеров.

| Тип | Формат | Срок жизни | Описание |
|-----|--------|------------|----------|
| **Access token** | JWT | 30 минут | Содержит `sub`, `type`, `sid` и сроки; сервер проверяет аккаунт и сессию в БД |
| **Refresh token** | opaque | 7 дней | В HttpOnly cookie; на сервере только хеш, ротация и отзыв; для гостя максимум 24 часа |

Производительность: проверка токена — не более 2 секунд, до 50 одновременных сессий.

## Гостевой режим

- Гость сканирует QR-код → создаётся `User` со `status = active`, `is_guest = true`, `guest_expires_at` (24 часа)
- Пользователь получает access JWT с `sub` (ID User) и `sid` (ID сессии); access хранится в памяти, refresh — в HttpOnly cookie
- При сканировании QR на другом терминале браузер отправляет токен → система проверяет `sub` и `sid` и узнаёт того же гостя
- Все результаты гостя привязываются к `id` этой записи
- **Авторизация:** если в течение 24 часов пользователь авторизуется через OAuth, OAuth-поля заполняются у той же записи, `is_guest` устанавливается в `false` — ID и результаты гостя сохраняются. Если аккаунт провайдера уже существует, вход выполняется в него, история гостя остаётся отдельно
- **Истечение:** если 24 часа прошли без авторизации, `guest_expires_at` истекает. Пользователь считается обезличенным (anonymized), данные остаются в системе (аналитика не удаляется), но связать этого пользователя с будущей OAuth-авторизацией нельзя

---

## Оффлайн-режим (нет Интернета у пользователя)

- **Отдельные точки доступа** (роутеры) раздают гостевой Wi-Fi
- На гостевом Wi-Fi разрешён доступ только к URL системы и сервисам VK/Яндекс (для OAuth)
- Пользователь подключается к Wi-Fi, сканирует QR с терминала → авторизация через OAuth работает
- Если гостевой Wi-Fi недоступен — только гостевой режим без авторизации

## API для интеграции

Централизованный auth-сервис предоставляет API для всех подсистем:

| Endpoint | Назначение |
|---|---|
| `GET /qr/scan` (планируется) | Сканирование QR и выбор способа входа; пока не реализовано |
| `POST /api/auth/user/guest` | Создание гостя с обязательным согласием; access в JSON, refresh в cookie |
| `GET /api/auth/user/oauth/{provider}` | Код от отдельного фронтенда + согласие; вход/привязка гостя, новая сессия |
| `POST /api/auth/user/refresh` | Ротация refresh-cookie с проверкой источника, получение нового access |
| `GET /token/validate` (планируется) | Отдельный endpoint проверки для внешних подсистем; пока не реализовано |
| `GET /api/user/info` | Данные текущего посетителя по access |
| `POST /api/auth/user/logout` | Отзыв текущей сессии по cookie + Origin/Referer |

## Хранение данных

- **PostgreSQL**
- Раздельное хранение:
  - Пользователи (гости и авторизованные в одной таблице)
  - Согласия пользователя

## Масштаб и производительность

- До 50 одновременных сессий
- До 10 000 пользователей в системе
- Проверка токена — не более 2 секунд

---

## Особые сценарии

- **Пользователь заблокирован в Яндекс/VK:** может использовать другого провайдера
- **Провайдер OAuth недоступен:** может использовать другого провайдера или гостевой режим
- **Деактивация аккаунта:** действие администратора, вход невозможен, данные сохранены
- **Обезличивание:** если гость не авторизовался за 24 часа, `guest_expires_at` истекает, данные остаются в системе, но связать пользователя с будущей авторизацией нельзя

## Взаимодействие

- Обслуживает все подсистемы и клиентские интерфейсы
- Передаёт данные профиля в **Цифровой профиль**
- Сенсорные стойки подключаются к единому auth через QR-код
