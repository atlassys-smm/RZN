# Подсистема «Идентификация и регистрация»

Инфраструктурный auth-сервис. Встраивается во все точки взаимодействия: терминалы, мобильные устройства, сенсорные стойки, LED. Выдаёт токены, проверяет credentials, обслуживает OAuth 2.0 через внешних провайдеров. Не имеет собственного клиентского фасада — его используют все подсистемы.

---

## Способы авторизации

- **OAuth 2.0 через внешних провайдеров:**
  - Яндекс ID (имя, email, аватар, дата рождения)
  - VK ID (имя, email, аватар, пол, дата рождения; покрывает ВКонтакте, Mail.ru, Одноклассники)
- **Гостевой режим** — без авторизации, по QR-коду, с возможностью последующей привязки к профилю
- Локальная регистрация по ID/паролю **не поддерживается**

---

## Регистрация и данные пользователя

- Автоматическая регистрация при первом входе через OAuth
- Данные из OAuth: имя, email, аватар, ID провайдера, пол, возраст (при доступности)
- **Согласие на обработку персональных данных:**
  - При первой авторизации пользователю показывается текущая активная версия согласия
  - Пользователь должен принять согласие для завершения регистрации
  - В `ConsentAcceptance` фиксируется: `user_id`, `consent_id` (ID версии согласия), `accepted_at`
  - При изменении текста согласия (новая версия) пользователь принимает новую версию при следующем входе
- Объединение аккаунтов из разных провайдеров — опционально (не обязательно)

---

## Токены и сессии

| Тип | Формат | Срок жизни | Описание |
|-----|--------|------------|----------|
| **Access token** | JWT | 30 минут | Проверяется локально подсистемами |
| **Refresh token** | opaque | 7 дней | Хранится на сервере, для обновления access token |
| **Гостевой токен** | JWT | 24 часа | Только `guest_id`, без профиля |

Производительность: проверка токена — не более 2 секунд, до 50 одновременных сессий.

---

## Гостевой режим

- Терминал генерирует `guest_id`, привязывает результаты к нему
- Гостевая сессия живёт 24 часа (пользователь может работать с разными терминалами)
- **Привязка к профилю:** когда пользователь авторизуется, система связывает `guest_id` с `user_id`, результаты переходят в профиль

---

## Оффлайн-режим (нет Интернета у пользователя)

- **Отдельные точки доступа** (роутеры) раздают гостевой Wi-Fi
- На гостевом Wi-Fi разрешён доступ только к URL системы и сервисам VK/Яндекс (для OAuth)
- Пользователь подключается к Wi-Fi, сканирует QR с терминала → авторизация через OAuth работает
- Если гостевой Wi-Fi недоступен — только гостевой режим без авторизации

---

## API для интеграции

Централизованный auth-сервис предоставляет API для всех подсистем:

| Endpoint | Назначение |
|---|---|
| `GET /authorize` | Начало OAuth-флоу (редирект на провайдера) |
| `GET /callback` | Callback от OAuth-провайдера |
| `POST /token/refresh` | Обновление access token по refresh token |
| `GET /token/validate` | Проверка JWT (для подсистем, которые не могут проверять локально) |
| `GET /userinfo` | Данные пользователя по токену |
| `GET /guest/qrcode` | Генерация QR для гостевого режима |
| `POST /guest/bind` | Привязка гостевой сессии к профилю |

---

## Хранение данных

- **PostgreSQL**
- Раздельное хранение:
  - Учётные записи (ID из OAuth, локальный `user_id`, статус)
  - Профили (история, результаты, логи)
  - Согласия пользователя

---

## Масштаб и производительность

- До 50 одновременных сессий
- До 10 000 пользователей в системе
- Проверка токена — не более 2 секунд

---

## Особые сценарии

- **Пользователь заблокирован в Яндекс/VK:** может использовать другого провайдера
- **Провайдер OAuth недоступен:** может использовать другого провайдера или гостевой режим
- **Удаление аккаунта:** не поддерживается
- **Обезличивание:** возврат информации без данных пользователя, только идентификатор

---

## Взаимодействие

- Обслуживает все подсистемы и клиентские интерфейсы
- Передаёт данные профиля в **Цифровой профиль**
- Сенсорные стойки подключаются к единому auth через QR-код
