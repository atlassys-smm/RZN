# Аватар профессий

Подсистема создаёт фотографии пользователей в образах профессий через внешний
сервис FaceAI, сохраняет результаты в Kernel и предоставляет их терминалу
и личному кабинету пользователя. Эталонные образы и их превью загружаются
через [CMS](../cms/profession-avatars.md).

## Аналитика

Создание задания, успешное сохранение, ошибка и истечение срока отправляются
в ClickHouse после commit. Прямая загрузка готового изображения учитывается
отдельно. WebSocket и REST-контракты сохранены.
[События, восемь графиков Metabase и правила расчёта](../analytics/dashboards/pak-detail/profession-avatars.md).

## Генерация через FaceAI

**Статус:** реализовано по документированному контракту FaceAI v2. Внешний сервис
пока не развёрнут; проверки выполняются с HTTP-моками. Прежний маршрут загрузки
готового изображения `/api/users/avatars` также сохранён.

Kernel (backend платформы) хранит пользователей, каталог эталонных образов и итоговые
фотографии. FaceAI — внешняя система генерации, которая принимает селфи и исходное
изображение выбранного образа, а результат передаёт в Kernel через webhook.
Терминал обращается только к Kernel и не получает ключи FaceAI.

### Идентификация образа и форматы

- `avatar_id` для FaceAI формируется из ID комплекта эталонных образов
  (`ProfessionAvatarTemplate.id`) и суффикса пола: `<id>_male` или `<id>_female`.
  Например, `42_male` и `42_female` обозначают два образа одного комплекта.
- `avatar_version` пока не используется для версионирования; Kernel передаёт `1`.
- Селфи и исходное изображение эталонного образа должны быть JPEG или PNG.
  WebP для исходных эталонов не допускается. В FaceAI передаётся исходное
  изображение выбранного пола, а не его превью.
- Результат FaceAI — JPEG. Ограничение JPEG/PNG относится к входным файлам FaceAI;
  превью в генерацию не передаются.

### Запрос терминала и получение результата

1. Терминал отправляет в Kernel запрос на генерацию с селфи, выбранным комплектом
   образов и полом. Терминал уже знает подключённого пользователя и использует
   собственный device-токен с ролью `2`. Kernel определяет пользователя по
   действующей QR-привязке через `X-Device-Connection-Id`.
2. `POST /api/users/avatar-generations` принимает multipart `template_id`, `gender`
   (`1` — мужской, `2` — женский) и `photo`. Kernel сохраняет отдельное задание,
   селфи и ID исходного файла выбранного образа; эталон не копируется. Фоновый
   обработчик отправляет запрос в FaceAI.
   Одновременно у пользователя может быть несколько активных генераций.
3. Каждый POST создаёт новое задание и возвращает `202` с новым UUID `request_id`
   и текущим статусом, включая повторный POST с теми же параметрами и селфи.
4. Перед созданием терминал подключается к `/api/avatar/ws?token=<device_jwt>`.
   Сокет требует роль `2` и передаёт `generation_status_changed` только для
   генераций своего устройства после успешного коммита. Payload содержит
   `user_id`, `generation_id`, `request_id`, `job_id`, `device_id`, `status`.
   Статусы: `1` — ожидает отправки, `2` — очередь FaceAI, `3` — обработка,
   `4` — готово, `5` — ошибка, `6` — истёк срок. Постоянный REST-опрос не нужен.
   По событию терминал читает `GET /api/users/avatar-generations/{request_id}`
   с device-токеном и действующей QR-привязкой владельца: при успехе получает
   `avatar_id`, `qr_token`, `file`, при неудаче — `error_code`. Этот же GET
   используется после переподключения; сокет не хранит историю событий.
   Чужое задание возвращает `404`. Ответы — `no-store`.
5. Kernel принимает результат FaceAI, сохраняет фотографию у себя и связывает её
   с пользователем и задачей. Терминал получает ссылку на файл Kernel.

### Создание задачи в FaceAI

`POST <FACEAI_BASE_URL>/api/v2/jobs`, Bearer `FACEAI_API_KEY`,
`multipart/form-data`:

| Поле | Содержание |
|------|------------|
| `request_id` | Уникальный ID запроса Kernel |
| `user_ref` | ID пользователя в Kernel |
| `avatar_id` | Составной идентификатор выбранного образа |
| `avatar_version` | `1` |
| `photo` | Файл селфи, JPEG или PNG |
| `avatar_image` | Файл выбранного эталонного образа, JPEG или PNG |

FaceAI возвращает `202 Accepted` с `job_id`, `request_id` и статусом `queued`.
Kernel сохраняет связь своей задачи с `job_id` FaceAI. Повтор с тем же `request_id`,
полями и байтами файлов возвращает существующую задачу (`200 OK`); изменённые данные
при том же `request_id` — `409 Conflict`. Переполненная очередь — `429` с `Retry-After`.

### Результат через webhook

Kernel принимает результат через `POST /api/faceai/webhook`. Полный адрес этого
маршрута и отдельный Bearer-токен задаются в FaceAI как `KERNEL_WEBHOOK_URL` и
`KERNEL_WEBHOOK_TOKEN`. В Kernel этот секрет называется `FACEAI_WEBHOOK_TOKEN`.
Он отличается от `FACEAI_API_KEY` для исходящих запросов Kernel.

Webhook всегда использует `multipart/form-data`:

| Поле | Содержание |
|------|------------|
| `event_id` | ID уведомления, неизменный при повторной доставке |
| `event` | `generation.completed` или `generation.failed` |
| `job_id` | ID задачи FaceAI |
| `request_id` | Исходный ID запроса Kernel |
| `user_ref` | ID пользователя |
| `avatar_id`, `avatar_version` | Выбранный образ и версия |
| `status` | `done` или `failed` |
| `image` | JPEG-файл при успехе |
| `expires_at` | Срок хранения результата в FaceAI при успехе; в Kernel не сохраняется |
| `error` | Код ошибки при неудаче, например `no_face_detected` |

Заголовок `X-FaceAI-Event-ID` дублирует `event_id`. При ошибке `image` и
`expires_at` отсутствуют. Kernel должен проверить Bearer-токен, найти свою задачу
по `request_id`, заблокировать её запись и сохранить результат или ошибку,
затем ответить `200 OK`. Для уже завершённого задания возвращается `200 OK`
без изменения результата и создания дубликата фотографии, независимо от `event_id`.

При сетевой ошибке или non-2xx ответе FaceAI повторяет доставку с тем же `event_id`
и байтами JPEG: через 5, 10, 20 секунд и далее, с интервалом не более часа,
до истечения срока хранения. Отдельное скачивание для обычного сценария не требуется.

### Резервная проверка и хранение

FaceAI предоставляет авторизованные через `FACEAI_API_KEY` маршруты:

- `GET /api/v2/jobs/{job_id}` — статус `queued`, `processing`, `done`, `failed`
  или `expired`;
- `GET /api/v2/jobs/{job_id}/image` — скачивание результата; после истечения
  срока хранения — `410 Gone`.

FaceAI удаляет исходники после обработки и по умолчанию хранит результат 24 часа
после завершения. Kernel должен принять и сохранить фотографию до истечения
этого срока. Swagger FaceAI: `/docs`, OpenAPI: `/openapi.json`, описание webhook:
**Webhooks → generation-result**. В интеграции используются оба идентификатора:
`request_id` Kernel и `job_id` FaceAI.

### Повторы, проверка и восстановление

- Задания сохраняются в PostgreSQL. Обработчик закрепляет
  задание временной арендой (не менее 120 секунд), повторно забирает его после
  сбоя процесса и не держит транзакцию БД во время запроса FaceAI. Поздний ответ
  обработчика с истёкшей арендой не перезаписывает новое состояние.
- Селфи сохраняется отдельно, эталон используется по исходному File.id без копии.
  Повтор отправки использует тот же `request_id` и исходные файлы задания.
  `429` учитывает `Retry-After`; сетевые и временные ошибки повторяются
  с увеличением задержки до 5 минут, в пределах срока задания.
- Webhook проверяет Bearer, `request_id`, `job_id`, пользователя, образ, версию
  и совпадение `event_id` в форме и заголовке. Неизвестное задание — `404`,
  несоответствия задаче — `409`, неверное тело — `422`. Повтор определяется по
  статусу заблокированной записи задания. Фактический формат результата проверяется как JPEG.
- Webhook может прийти раньше HTTP-ответа создания: он сам связывает `job_id`.
  Повторные или конкурентные события и гонка с опросом не создают второй
  `UserAvatar`. Результат и статус задания фиксируются общей транзакцией.
- После получения `job_id` Kernel опрашивает статус FaceAI по умолчанию раз
  в 60 секунд. При `done` скачивает JPEG и сохраняет его, даже если webhook
  потерялся. Поздний webhook подтверждается `200` без второго результата.
- Максимальный срок задания Kernel — **24 часа с создания**, независимо от
  срока хранения результата FaceAI. По дедлайну незавершённое задание становится
  `6` / `generation_timeout`; внешний `expired` или `410` —
  `6` / `faceai_result_expired`. Поздний результат не меняет завершённое задание.

### Настройки Kernel

| Переменная | Значение по умолчанию | Назначение |
|------------|----------------------|------------|
| `FACEAI_BASE_URL` | пусто | Домен/base URL FaceAI, без `/api/v2/jobs` |
| `FACEAI_API_KEY` | пусто | Bearer-токен исходящих запросов |
| `FACEAI_WEBHOOK_TOKEN` | пусто в шаблоне env | Отдельный секрет входящего webhook |
| `FACEAI_HTTP_TIMEOUT_SECONDS` | 30 | Таймаут HTTP FaceAI |
| `FACEAI_POLL_SECONDS` | 60 | Интервал резервной проверки |
| `FACEAI_WORKER_INTERVAL_SECONDS` | 5 | Интервал обхода очереди |

Если адрес или API-ключ пусты, фоновая отправка отключена; задание создаётся
в статусе ожидания и сохраняет дедлайн 24 часа. Фоновое завершение по дедлайну
работает и без настройки FaceAI, с уведомлением через сокет. Если не задан токен webhook,
его маршрут возвращает `503`. После настройки
env API нужно обновить для загрузки новых значений. Секреты терминалу не выдаются.
Превью необязательны; формат JPEG/PNG проверяется по MIME-типу и сигнатуре без декодирования и Pillow.
Отдельного лимита размера FaceAI нет; при сохранении действует прежний общий
лимит файлового сервиса. Требования к разрешению и пропорциям из CMS
остаются рекомендациями по качеству.

Схема хранения: [задания генерации](../../entities/avatar-generations.md).

## Демонстрационное прохождение через API

`simulate_avatars` эмулирует успешную генерацию **без запросов к внешнему FaceAI**.
У команды нет режима реальной генерации и нет переключения на внешний сервис.
Она создаёт demo-гостя, подключает его по QR к свободному AVATAR-устройству,
отправляет запрос локальной эмуляции и проверяет сохранённый результат и JPEG.

Команда использует `DEMO_ADMIN_LOGIN`, `DEMO_ADMIN_PASS`, `DEMO_API_URL`
и `AUTH_ALLOWED_ORIGINS`, как остальные `simulate_*`. Нужны администратор с ролью
`1`, активное свободное устройство с ролью `AVATAR (2)`, существующие комплекты
образов и опубликованное согласие. Настройки `FACEAI_*`, внешний сервер и webhook
для эмуляции не нужны. Даже при заполненных настройках настоящего FaceAI
demo-обмен остаётся локальным.

```sh
docker compose exec -T api python -m app.cli.simulate_avatars
docker compose exec -T api python -m app.cli.simulate_avatars --template-id 10 --device-id 3 --gender male
docker compose exec -T api python -m app.cli.simulate_avatars --template-id 10,11 --gender both --result-photo /app/storage/infra/demo-result.jpg --report /app/storage/infra/avatars-run.json --download-dir /app/storage/infra
docker compose exec -T api python -m app.cli.simulate_avatars --photo /app/storage/infra/selfie.jpg --profession-count 2 --seed 42
```

ID в примерах заменяются на существующие. `--template-id` означает
`ProfessionAvatarTemplate.id`, а не `profession_id`; каталог — `GET /api/avatars`.
Без `--photo` используется встроенный синтетический портрет
`app/cli/data/avatar/default.png`; путь определяется относительно модуля,
независимо от текущего каталога. Для своего фото пути задаются внутри
контейнера: `storage/infra/selfie.jpg` на хосте доступен
как `/app/storage/infra/selfie.jpg`. Один запуск создаёт одного гостя. По умолчанию
выбираются один случайный комплект и один случайный пол. `both` создаёт два задания
на каждый комплект. Устройства, комплекты и согласия не создаются и не изменяются.

### Локальная отправка и успешный ответ

1. Через обычный API выполняются вход администратора и гостя, подбор свободного
   устройства, выдача его JWT, создание QR и подтверждение гостем. Занятый терминал
   не отключается. Подтверждаются пользователь и `connection_id` привязки.
2. Администратор вызывает `POST /api/cms/avatar-generations/simulate` с multipart
   `device_id`, `template_id`, `gender`, `photo`, необязательным `result_photo`
   и заголовком `X-Device-Connection-Id`. Устройство и QR-привязка проверяются заново.
   Пользователь или обычный device JWT этот маршрут вызвать не могут.
3. Backend использует обычную сериализацию FaceAI v2, но передаёт запросы в
   `httpx.MockTransport` внутри процесса: `POST /api/v2/jobs` получает `202 queued`,
   `GET /api/v2/jobs/<job_id>` — `200 done`, `GET .../image` — `200 image/jpeg`.
   Сокеты не открываются, реальные URL и ключи FaceAI в этот обмен не передаются.
4. JPEG результата берётся из `--result-photo`; если он не задан, копируется
   основной исходник выбранного пола, PNG преобразуется в JPEG. Эмуляция не
   синтезирует новое лицо и не изменяет фотографию с помощью нейросети.
5. Задание, селфи, UserAvatar и JPEG сохраняются одной транзакцией сразу со
   статусом `4`. Незавершённое demo-задание не коммитится: обычный фоновый worker
   его не видит и не может отправить наружу. Аналитика начала и завершения
   отправляется после commit; уведомление терминалу содержит готовый результат.
6. CLI проверяет аватар через `/me/avatars/{avatar_id}` от имени гостя и скачивает
   JPEG по подписанной ссылке. В `finally` отключается только собственная QR-привязка
   с её `connection_id`, затем завершаются созданные staff/user сессии авторизации.

Сохраняются настоящие demo-задания, результаты, файлы и события в выбранном API.
Обычный маршрут `/api/users/avatar-generations` команда не вызывает. Ожидания
внешнего ответа, параметров `--timeout`/`--poll-interval` и реального режима нет.
Сетевая/HTTP-ошибка не вызывает повтор POST; следующий образ при ошибке не запускается.
Обычная работа модуля вне этой команды остаётся без изменений.

| Параметр | Поведение |
|----------|-----------|
| `--photo` | Необязательное селфи JPEG/PNG. По умолчанию встроенный синтетический портрет `app/cli/data/avatar/default.png`. Сигнатура проверяется до первого HTTP-запроса; фото используется во всех заданиях запуска. |
| `--result-photo` | Необязательный JPEG, возвращаемый локальным FaceAI-моком. По умолчанию — основной исходник выбранного образа. |
| `--template-id` | Один ID, список через запятую или несколько флагов; порядок сохраняется. Дубликат, отсутствующий комплект или недоступная профессия — ошибка. |
| `--profession-count` | Число случайных доступных комплектов, не больше числа подходящих; по умолчанию 1. Не сочетается с `--template-id`. |
| `--device-id` | Активное свободное устройство с ролью 2; без параметра — случайный подбор. Чужая QR-привязка не разрывается. |
| `--gender` | `random` по умолчанию, `male` (1), `female` (2) или `both` (сначала 1, затем 2). |
| `--seed` | Воспроизводимый выбор комплектов, устройства и пола при одинаковых исходных данных. |
| `--report` | Новый JSON-файл: `faceai_simulated=true`, ID гостя, устройства, согласия, комплектов, заданий и аватаров, статусы, прогресс и ошибки. |
| `--download-dir` | Существующий каталог для `avatar-<request_id>.jpg`. Без параметра JPEG скачивается и проверяется без записи на диск. |
| `--base-url`, `--origin` | Корень API с `/api` из `DEMO_API_URL` и первый `AUTH_ALLOWED_ORIGINS` по умолчанию. |

Отчёт и JPEG не перезаписывают существующие файлы. JWT, пароли, QR-коды,
`connection_id`, `qr_token` и подписанные URL не сохраняются в отчёт и вывод.
Код выхода `0` — все результаты проверены; `1` — ошибка выполнения;
`2` — ошибка параметров; `130` — прерывание. Готовые задания и результаты не удаляются.


## Аватары пользователя

Для личного кабинета используется Bearer user access-токен:

- `GET /api/me/avatars` — свои аватары, включая сохранённые результаты FaceAI.
  Необязательный `profession_id` фильтрует по профессии. Пагинация — `limit`
  (по умолчанию 20) и `offset`; `total` считается после фильтра до пагинации.
- `GET /api/me/avatars/{avatar_id}` — свой аватар по числовому ID.
- `DELETE /api/me/avatars/{avatar_id}` — удалить свой аватар и итоговый файл,
  ответ `204`. Чужой или отсутствующий аватар возвращает `404`.

В DELETE используется `id` элемента списка или `avatar_id` готовой генерации,
а не UUID `request_id`. Исходники задания сохраняются. Поздний webhook
не восстанавливает уже удалённый аватар.
