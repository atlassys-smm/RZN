# Подсистема «Аналитика и отчётность»

Подсистема собирает внутренние события бэкенда в ClickHouse. Metabase читает
SQL-представления и выводит показатели в коллекциях и дашбордах.
Сейчас события отправляют индивидуальная викторина и командная игра
LED-медиаплатформы (`module_id=1` и `module_id=2`). «Профессии в действии»
(`module_id=3`) фиксируют старт показа, подключение участника и завершение.
ПрофСтарт отправляет события при старте, ответе, завершении, явном прерывании и сохранении
рекомендаций профессий (`module_id=4`). Обратная связь отправляет реальные старты,
итоговые оценки и окончания (`module_id=5`). «Аватар профессий» (`module_id=6`)
отправляет создание задания, успех, ошибку, истечение срока и отдельную загрузку
готового изображения; [контракт и графики](analytics/dashboards/pak-detail/profession-avatars.md).

## Сбор и доставка

Сервисы вызывают `app.services.analytics.emit_event` после бизнес-операции.
Функция сериализует событие и помещает его в ограниченную `asyncio.Queue`;
HTTP-запрос пользователя не ждёт ClickHouse. Фоновый отправитель собирает пакеты,
отправляет их по HTTP и ждёт подтверждения записи. Неудачные попытки повторяются
с тем же содержимым и токеном вставки.

Очередь находится в памяти процесса API. При аварии, перезагрузке, переполнении
или исчерпании повторов события могут теряться. Постановка события не входит
в транзакцию бизнес-операции. Внешние модули отправляют события через
`POST /api/analytics/external/events`. Маршрут принимает токен администратора
или JWT активного устройства с ролью `EXTERNAL_APPS (5)`. Ответ `202`
подтверждает приём в очередь. [Контракт внешних событий](../entities/analytics.md#analyticsevent).

## События и хранилище

Все события записываются в физическую таблицу `analytics.events`.
SQL-представления выделяют данные подключённых модулей и учитывают повторы по ID события.
Числовые коды действий и функциональных модулей задаются
через IntEnum. UUID конкретного факта находится в `id`.
Контракт полей, payload и правила расчёта описаны в
[AnalyticsEvent](../entities/analytics.md), типы — в
[справочнике событий](../references/analytics-event-types.md).

| Событие | Что фиксирует |
|---|---|
| `1` — SESSION_STARTED | Фактический старт; для викторины — состав участников и команд, для ПрофСтарт — версия теста |
| `2` — PARTICIPANT_JOINED | Регистрацию нового участника |
| `3` — ANSWER_EVALUATED | Правильность оценённого ответа участника или команды |
| `4` — SESSION_FINISHED | Завершение сессии и длительность. Для «Профессий в действии» учитывается и ручная остановка. Для ПрофСтарта сохраняется снимок показателей групп |
| `5` — PROFESSION_RECOMMENDED | Одну профессию из результата теста ПрофСтарт: тест, версия, профессия, score и позиция |
| `6` — ANSWER_SUBMITTED | Личный принятый ответ командной викторины без содержимого, вариант и время ответа ПрофСтарт либо итоговую числовую оценку rating_scale в анкете |
| `7` — SURVEY_STARTED | Реальное начало заполнения анкеты |
| `8` — SURVEY_FINISHED | Сохранение готовой анкеты и длительность |
| `9` — SESSION_ABANDONED | Явное прерывание ПрофСтарт пользователем или оператором |
| `13` — AVATAR_GENERATION_FAILED | Ошибку задания генерации Аватара |
| `14` — AVATAR_GENERATION_EXPIRED | Истечение срока задания или результата FaceAI |
| `15` — AVATAR_UPLOADED | Отдельную загрузку готового изображения |

Тексты, сложность, варианты вопросов, ответы и игровые баллы викторины
в аналитику не передаются. ПрофСтарт передаёт выбранный вариант, вклад ответа,
снимок показателей групп и нормированный score рекомендации. Его графики
подключены через четыре представления ClickHouse; [контракт и расчёты](analytics/dashboards/pak-detail/profstart.md).
Поле `is_guest` фиксирует гостевой статус на момент события; старые события
сохраняют NULL. Посещаемость считает уникальные user_id через `visitor_activity`,
включая участников стартового снимка викторины.
Срок хранения событий автоматически не ограничен. Производительность на целевом
объёме данных нагрузочными тестами пока не подтверждена.

## Отчёты и доступ

Metabase хранит пользователей, подключения, вопросы, дашборды и настройки
в своей базе `metabase` существующего PostgreSQL проекта. Показатели читает
из ClickHouse через пользователя `analytics_reader` с правом SELECT.

Корневая коллекция «Аналитика» содержит группы показателей административного
портала. Подключено 92 запроса: 30 для викторин, заставки и общих показателей LED,
четыре для вовлечённости, девять детальных и два общих для обратной связи,
13 для ПрофСтарт, 10 для сводки модулей, четыре для посещаемости, два для
тепловой диаграммы, 10 для востребованности организаций, профессий и направлений
образования, восемь для Аватара. Остальные 30 показателей — заготовки без запросов.
[Полный состав](analytics/clickhouse-metabase.md#коллекции-и-подключённые-показатели).

Бэкенд предоставляет `GET /api/analytics/catalog`: постоянные ключи связаны
с ID и type коллекций, дашбордов и графиков. Запрос требует действующий токен
любой сущности и читает локальный реестр. Описания объектов и результаты
запросов фронтенд получает непосредственно из Metabase с отдельной авторизацией.

JSON и PDF карьерного трека используют события, в которых `is_guest = false`
за выбранный период. SQL отчёта учитывает сохранённые рекомендации пользователей
с `service_user IS NULL`. Авторизованный демо-пользователь проходит этот отбор
при наличии события за период и сохранённых рекомендаций с положительными баллами.

## Конфигурация и развёртывание

Скрипты запускаются через `docker compose exec api python`, используют
окружение контейнера из корневого `.env` и внутренние адреса сервисов Compose.
SQL-миграции ClickHouse и JSON-файлы коллекций Metabase находятся в `infra`.
Журнал миграций, реестр ID, блокировки, резервные копии и диагностика —
в `storage/infra`, отдельно по компонентам.

Команды, настройки, порядок развёртывания и входа описаны на странице
[ClickHouse и Metabase](analytics/clickhouse-metabase.md).

## Демо-команды { #demo-commands }

Запускайте команды из корня бэкенда через `docker compose exec -T api`.
В окружении контейнера задайте `DEMO_ADMIN_LOGIN` и `DEMO_ADMIN_PASS`
действующего администратора. `DEMO_API_URL` задаёт корень API с `/api`
(по умолчанию `http://localhost:8000/api`). Команды используют первый
`AUTH_ALLOWED_ORIGINS`. Адрес и Origin можно задать через `--base-url` и
`--origin`. Для событий в ClickHouse включите `ANALYTICS_ENABLED=true`
и настройте доставку, как описано в разделе [ClickHouse и Metabase](analytics/clickhouse-metabase.md).

| Команда | Что она делает |
|---|---|
| `simulate_quiz` | [Проходит индивидуальную викторину](led-platform/quiz.md) |
| `simulate_profstart` | [Проходит тесты ПрофСтарта](profstart/test-flow.md) |
| `simulate_video` | [Проходит «Профессии в действии»](../interfaces/operator-tablet/professions.md) |
| `simulate_feedback` | [Заполняет активную анкету](feedback/client.md) |
| `simulate_views` | [Просматривает карточки справочников](cms/references.md) |
| `simulate_avatars` | [Эмулирует генерацию аватара](profession-avatars/index.md) |
| `simulate_unity` | [Отправляет демо-события модулей Unity](#demo-unity) |
| `simulate_user` | [Запускает сценарии для одного авторизованного пользователя](#demo-user-run) |

Отдельные команды по умолчанию создают нового гостя. Флаг `--authorized`
создаёт отдельный демо-аккаунт с `is_guest=false` и пользовательским токеном.
Имя и фамилия выбираются случайно из двух списков по 15 вариантов. Форма
фамилии «-ов» или «-ова» соответствует имени. Команды выбирают действующую
опубликованную версию согласия. Сначала ищут по `AUTH_CONSENT_CODE`
(по умолчанию `personal_data`), затем используют самую новую действующую
версию среди остальных типов. [Авторизация демо-пользователя](auth-sessions.md#demo-user).

`--date 2026-11-20` задаёт старт активности на 12:00 МСК.
`--date 2026-11-20T14:30:00+03:00` задаёт точное время начала. Для времени
без часового пояса используется МСК. Даты записей прохождения в PostgreSQL
и событий в ClickHouse учитывают время, прошедшее с начала сценария.
Сроки действия токенов, Redis-таймеры и фоновые задачи работают по текущему
времени. Без `--date` текущая дата используется и для активности.

```sh
docker compose exec -T api python -m app.cli.simulate_quiz --authorized --date 2026-11-20
```

В отдельных командах `--report` сохраняет результат и прогресс в новый
JSON-файл. Путь `/app/storage/infra/quiz-run.json` внутри контейнера
соответствует `storage/infra/quiz-run.json` на хосте. Запуски добавляют
записи и события в систему. В аналитике выбирайте период, включающий дату
этой активности. События становятся доступны после фоновой доставки.

### Демо-события Unity { #demo-unity }

`simulate_unity` создаёт одного пользователя и отправляет события через
API внешней аналитики. У каждого прохождения свой UUID. Администратор
отправляет события с `user_id` созданного пользователя и `occurred_at`.
Сервер берёт `is_guest` из PostgreSQL. При таком запуске `device_id` равен `NULL`.

| Подкоманда | События |
|---|---|
| `tree` · Древо профессий (`module_id=7`) | Старт (`1`), открытие карточек профессий (`11`), завершение (`4`) |
| `map` · Интерактивная карта региона (`module_id=8`) | Старт (`1`), выбор территории (`17`), открытие карточек работодателей и учебных заведений (`16`), завершение (`4`) |
| `profbattle` · Профбаттл (`module_id=9`) | Старт (`1`) и завершение (`4`) с `mode` и `case_code` |

`--sessions` задаёт число прохождений для одного пользователя. По умолчанию
выполняется одно. `--views` для `tree` и `map` задаёт число открытых карточек
на прохождение. По умолчанию выбираются до трёх карточек. У `profbattle`
`--mode` принимает `individual` или `group`, а `--case-code` задаёт код
кейса. По умолчанию выбирается случайный кейс индивидуального режима.
`--seed` позволяет повторить выбор контента по тем же каталогам.

```sh
docker compose exec -T api python -m app.cli.simulate_unity tree --authorized --views 5 --date 2026-11-20
docker compose exec -T api python -m app.cli.simulate_unity map --authorized --sessions 2 --views 4
docker compose exec -T api python -m app.cli.simulate_unity profbattle --authorized --mode group --case-code it-team
```

### Сквозной прогон за одного пользователя { #demo-user-run }

`simulate_user` создаёт одного авторизованного демо-пользователя и использует
его ID во всех сценариях. Параметр `--user-id` позволяет пройти те же сценарии
за существующего активного авторизованного пользователя. Команда открывает
отдельную демо-сессию администратора для этого ID и закрывает её по окончании.
Уже пройденные типы тестов ПрофСтарта пропускаются. При незавершённом прохождении
команда пропускает ПрофСтарт и сохраняет прогресс пользователя.

В ходе прогона пользователь просматривает справочники, проходит активные
тесты ПрофСтарта, играет от двух до пяти индивидуальных викторин, проходит
видеосценарии, заполняет анкету, эмулирует аватар и отправляет события трёх
модулей Unity. Первая викторина проходит с правильными ответами, следующие
со случайными. При одинаковом `--seed` и исходных данных выбор повторяется.

```sh
docker compose exec -T api python -m app.cli.simulate_user --quiz-count 2 --seed 42 --date 2026-11-20
docker compose exec -T api python -m app.cli.simulate_user --user-id 42 --quiz-count 2
```

Для викторины и видео можно указать свободное устройство `QUIZ_VIDEO (1)`
через `--play-device-id`. Для аватаров `--avatar-device-id` выбирает
свободное устройство `AVATAR (2)`, а `--photo` задаёт файл внутри контейнера
для локальной эмуляции FaceAI. По умолчанию используется встроенный портрет.

Команда выводит ID пользователя, ошибки и итоговое число завершённых
сценариев в консоль. При ошибке викторины или видеопоказа команда пытается
завершить созданную сессию по её ID, чтобы освободить устройство. Если завершить
сессию не удалось, команда выводит её ID и ошибку. Затем она пробует выполнить
остальные сценарии и возвращает код `1` по итогам прогона. При полном прохождении
код равен `0`. Уже записанные данные остаются доступны по этому `user_id`.

## Требования к показателям

Состав показателей административного портала описан в
[требованиях к дашбордам](../interfaces/admin-portal/dashboards.md).
[Раздел дашбордов](analytics/dashboards.md) описывает целевой состав отчётов;
наличие показателя в требованиях не означает, что его источник данных подключён.
