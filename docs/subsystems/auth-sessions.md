# Авторизация и серверные сессии

Реализованы вход сотрудников по email/паролю, создание гостя с согласием, выдача access, refresh, logout и сведения о текущем посетителе. Реализован OAuth Яндекс ID/VK ID с обменом одноразового кода на сервере.

## Токены и хранение

- Access — JWT, максимум 30 минут: `sub` (ID), `type` (`user`/`staff`), `sid` (сессия), `iat`, `exp`, `iss`, `aud`, `jti`. В JSON также возвращаются `token_type=bearer`, `expires_in`. Refresh в JSON отсутствует.
- Refresh — криптографически случайная строка (32 случайных байта), только в HttpOnly cookie. PostgreSQL хранит SHA-256 хеш, ID сессии, время создания и использования; исходный refresh не хранится и не журналируется.
- `auth_sessions`: UUID, ровно один владелец (`user_id` или `staff_user_id`), создание, абсолютное истечение, отзыв. `auth_refresh_tokens`: история одноразовых refresh. Использованные записи сохраняются для обнаружения повторного использования; будущая очистка допустима после окончания сессии.
- Сессия сотрудника/OAuth-пользователя — 7 дней от входа. Ротация не продлевает срок. Сессия гостя и его access ограничены `guest_expires_at` (24 часа). После истечения нужен новый гость; старые результаты сохраняются, восстановление связи и привязка старого гостя к OAuth запрещены.
- Access передаётся в `Authorization: Bearer ...`; refresh не принимается для доступа к API. Общая проверка `app/core/auth.py` проверяет подпись/claims, тип, владельца, актуальный статус аккаунта, срок гостя и действительность сессии в PostgreSQL. JWT без обязательных claims, с неправильным `sub`, чужим владельцем или отозванной сессией → `401`.

## Cookie, CORS и проверка источника

| Клиент | Cookie | Path | Маршруты сессии |
| --- | --- | --- | --- |
| Сотрудник | `staff_refresh` | `/api/auth` | `/api/auth/{refresh,logout}` |
| Посетитель | `user_refresh` | `/api/auth/user` | `/api/auth/user/{refresh,logout}` |

Cookie имеют `HttpOnly`, `SameSite=Lax`, по умолчанию `Secure`, без Domain (host-only). Оба аккаунта могут одновременно существовать в браузере. Cookie одного типа не подходит для другого. Access хранить в памяти клиента, а не в localStorage. Все ответы `/api/auth/*`, включая ошибки, имеют `Cache-Control: no-store`.

Настройки:

- `AUTH_COOKIE_SECURE=true` — production HTTPS. Для локальной разработки по HTTP явно задать `false`; пример в `.env.example`. Рабочий `.env` автоматически не изменяется.
- `AUTH_COOKIE_SAMESITE=lax`. Если фронтенд/API находятся на разных sites, нужен `none` вместе с HTTPS/`Secure=true` (иначе конфигурация отклоняется). Разные порты одного хоста сами по себе не означают разные sites; `localhost` и `127.0.0.1` не взаимозаменяемы.
- `AUTH_ALLOWED_ORIGINS` — JSON-массив полных origins со схемой и портом, без wildcard. Общий список для CORS и проверки источника; указать адреса фронтенда. Для запросов Swagger добавить origin API. `credentials: 'include'` обязателен на фронте.
- `AUTH_CONSENT_CODE=personal_data` — код для выбора текста согласия на фронтенде; API проверяет только существование переданной версии.

Login, создание гостя, refresh и logout требуют разрешённый `Origin`; при его отсутствии проверяется origin `Referer`. Отсутствующий/чужой источник → `403`, сессия и cookie сохраняются. Origin имеет приоритет: нельзя заменить чужой Origin разрешённым Referer. Ошибка разбора Referer также даёт `403`.

Отдельный CSRF-токен, заголовок `X-CSRF-Token` и endpoints `/csrf` удалены. Защита от запросов с чужих сайтов основана на обязательной проверке Origin/Referer и SameSite. Проверку источника нельзя отключать при переходе на `SameSite=None`.

После перезагрузки страницы клиент сразу выполняет refresh с `credentials: 'include'` и получает access. Дополнительный запрос за токеном не нужен.

## Refresh и logout

`POST .../refresh`: тело не требуется, refresh берётся только из cookie, доверенный источник — из Origin/Referer. Сервер блокирует строку сессии в транзакции, повторно читает refresh, проверяет аккаунт/сроки, помечает старый токен использованным и создаёт новый. Ответ содержит новый access, а `Set-Cookie` заменяет refresh.

Повторное использование старого refresh с разрешённого источника отзывает всю эту сессию, включая её новые токены, и возвращает `401`. Изменение статуса на blocked/deactivated немедленно запрещает access и refresh. Неизвестный/истёкший/отозванный refresh → `401` и удаление соответствующей cookie. Две вкладки должны координировать refresh: параллельные запросы с одним токеном считаются повторным использованием.

`POST .../logout`: cookie + доверенный Origin/Referer; отзывает текущую сессию, удаляет cookie, возвращает `204`. Её access перестаёт работать сразу при следующей серверной проверке. Другие сессии не отзываются. Повтор с уже отозванной, но известной cookie также возвращает `204`; без действительного идентификатора cookie — `401`.

Пример фронтенда (пользователь):

```javascript
const refreshed = await fetch('/api/auth/user/refresh', {
  method: 'POST', credentials: 'include',
});
if (!refreshed.ok) throw new Error('Сессия недействительна');
const { access_token } = await refreshed.json();
// Последующие запросы: Authorization: `Bearer ${access_token}`.
```

## Создание гостя и сотрудников

`POST /api/auth/user/guest` требует JSON `consent_version_id` и `consent_accepted: true`. Проверяется только существование указанной версии согласия. Тип, статус, дата вступления в силу и актуальность версии не проверяются; черновик, архивная, будущая или устаревшая версия допускаются. Несуществующая версия или отказ → `422`, пользователь не создаётся. User, ConsentAcceptance (с IP непосредственного клиента) и сессия сохраняются одной транзакцией. Фронтенд находит тип с кодом AUTH_CONSENT_CODE через `GET /api/consents/types`, затем получает текст и ID версии через `GET /api/consents/types/{type_id}/versions/active`; текст сначала показывается пользователю. За reverse proxy IP требует отдельно настроенного доверия к proxy headers.

`POST /api/auth/login`: email/пароль; заблокированный сотрудник и неверные данные → одинаковый `401`. Email нормализуется для поиска/уникальности. Пароль сохраняется хешем bcrypt с предварительным SHA-256/base64, что поддерживает длинные пароли без обрезания. Проверок сложности, временных паролей, обязательной смены и отправки email пока нет.

`POST /api/auth/staff` доступен активному admin через access; неверный токен → `401`, другая роль → `403`, повтор email → `409`, некорректная роль → `422`. Текущая роль читается из БД, не из claims JWT.

Первого администратора создать интерактивно (пароль не передавать аргументом):

```powershell
docker compose exec api python -m app.cli.create_admin --email admin@example.org --first-name Admin --last-name User
```

## OAuth Яндекс ID / VK ID

Фронтенд — отдельное приложение. Он показывает согласие, запускает OAuth у провайдера, сохраняет и проверяет `state` при возвращении. Сервер не создаёт попытки OAuth и не выдаёт URL провайдера; маршрутов authorize/callback нет.

После успешного входа фронтенд вызывает `GET /api/auth/user/oauth/{provider}` с `credentials: include`:

| Провайдер | Query-параметры |
|---|---|
| Яндекс | `token` — одноразовый код, `consent_version_id`, `consent_accepted=true` |
| VK | `token` — одноразовый код, `device_id`, `state`, `redirect_uri`, `consent_version_id`, `consent_accepted=true` |

Чтобы сохранить действующего гостя, фронтенд передаёт его access в `Authorization: Bearer ...`. Истёкший или недействительный access возвращает `401`; после восстановления входа либо без старого access запрос можно выполнить заново. Без access сервер не связывает OAuth с прежним гостем. Проверяются доверенный Origin/Referer и только существование версии согласия, без требований к её активности. Redirect URI VK должен совпадать с использованным фронтендом при получении кода и зарегистрированным в VK; его origin должен входить в `AUTH_ALLOWED_ORIGINS`.

API обменивает код на токен провайдера и получает профиль. Для VK сервер проверяет совпадение возвращённого state и ID пользователя в токене/профиле; проверка state с исходной попыткой выполняется фронтендом. Одноразовость кода контролирует провайдер. Токены провайдеров не сохраняются в БД и не возвращаются клиенту. API записывает пользователя, согласие и новую сессию в одной транзакции, возвращает `user_id`, `is_guest=false`, access и срок, устанавливает refresh-cookie.

Пользователь ищется по `(oauth_provider, oauth_provider_id)`, без объединения по email. Существующий активный OAuth-аккаунт имеет приоритет: вход выполняется в него, гостевая запись и её результаты остаются отдельно. Если аккаунта нет, действующий гость превращается в авторизованного с тем же ID. После истечения 24 часов старый гость не привязывается. Исходная сессия повторно проверяется в транзакции; после успеха отзывается, выдаётся новая на 7 дней. Другие сессии существующего OAuth-аккаунта сохраняются. Конкурентные входы сериализуются advisory-блокировкой PostgreSQL. Смена OAuth-аккаунта у уже авторизованного User возвращает `409`.

Сохраняются имя (`first_name`), фамилия (`last_name`), email, пол и полная дата рождения, если предоставлены. Имя и фамилия берутся из отдельных полей провайдера, каждое ограничено 255 символами. В `avatar_url` сохраняется ссылка аватара провайдера: у Яндекса она формируется из `default_avatar_id` (размер `islands-200`), у VK берётся из `user.avatar`. При следующем входе отличающаяся непустая ссылка обновляется. Для Яндекса требуется доступ к портрету; `is_avatar_empty=true` не заменяет прежний аватар. Файлы не скачиваются. Отсутствующие необязательные данные не стирают ранее сохранённые значения. `GET /api/user/info` возвращает `first_name` и `last_name`, оба допускают `null`.

Миграция `0054` переименовывает прежнее `users.name` в `first_name` без изменения содержимого и добавляет nullable `last_name`. Фамилия из старой строки не угадывается. При откате имя и фамилия объединяются через пробел; если результат превышает прежний лимит 255 символов, PostgreSQL отклоняет откат без усечения данных.

Настройки backend `.env`: `OAUTH_YANDEX_CLIENT_ID`, `OAUTH_YANDEX_CLIENT_SECRET`, `OAUTH_VK_CLIENT_ID`, `OAUTH_VK_CODE_VERIFIER`. VK verifier берётся из конфигурации, как в PHP: фронтенд должен использовать соответствующий PKCE challenge. Параметра code_verifier у API нет. Для Яндекса используется обмен кода с client_secret, как в PHP. Redirect URI ведёт на отдельный фронтенд; его настройки и scopes задаются там, а URI регистрируется у провайдера. Backend больше не использует OAUTH_*_REDIRECT_URI/OAUTH_*_SCOPE.

Фронтенд должен входить в `AUTH_ALLOWED_ORIGINS`. Для разных сайтов refresh требует `AUTH_COOKIE_SAMESITE=none`, `AUTH_COOKIE_SECURE=true`, HTTPS и `credentials: include`; ограничения сторонних cookies браузера также учитываются фронтендом. Все ответы авторизации имеют `Cache-Control: no-store`. Query-параметр token содержит чувствительный код: фронтенд и прокси не должны сохранять полный URL в журналах.

Compose передаёт `.env` при создании контейнера; изменение файла не обновляет окружение уже работающего API. Пересоздание API выполняется отдельно после проверки миграций.

Ошибки: `400` — отказ провайдера, недействительный код или параметры VK; `401` — недействительный access, отозванная сессия или заблокированный аккаунт; `403` — источник запроса; `422` — параметры/согласие; `503` — отсутствующие настройки или провайдер недоступен. Детали ответов провайдера и секреты в HTTP-ошибки не включаются.

Обмен кода соответствует [Яндекс ID](https://yandex.ru/dev/id/doc/ru/codes/code-url) и [официальному SDK VK ID](https://github.com/VKCOM/vkid-web-sdk/blob/master/src/auth/auth.ts).

## Структура реализации

OAuth-сценарии находятся в `app/services/auth/oauth.py`, HTTP-обмен и преобразование профиля — в `app/services/auth/providers.py`. Общая точка входа `fetch_profile` выбирает обработчик из `PROFILE_FETCHERS`. `fetch_yandex_profile` и `fetch_vk_profile` независимо проверяют настройки и параметры, обменивают код и преобразуют профиль; проверки state, redirect_uri и ID VK находятся в обработчике VK. Новый обработчик добавляется в реестр, а сохранение нормализованного `Profile` остаётся общим в `oauth.py` (также требуется добавить значение провайдера в enum и соответствие в `oauth.PROVIDERS`). Остальные бизнес-сценарии и транзакции находятся в `app/services/auth/service.py`: login_staff, register_staff, register_guest, refresh_session, logout_session. Маршруты выполняют вызовы сервисов и оформляют HTTP-ответы/cookie; ORM/SQL, commit/rollback и обработка конфликтов БД в них отсутствуют. Доменные ошибки сервисов переводятся в HTTP-коды общим `AuthRoute` в `app/api/auth/errors.py`. Проверка токенов устройств также находится в сервисе.

## Подключение к игре по QR

QR открывает страницу фронтенда с ID сессии. При отсутствии действующего входа фронтенд показывает выбор гостевого входа/OAuth и согласие. Гостевой вход выполняется через `POST /api/auth/user/guest`; OAuth запускается фронтендом и завершается запросом `/api/auth/user/oauth/{provider}`. Refresh сохраняется в HttpOnly cookie, access используется в `Authorization: Bearer <access_token>`. После перезагрузки страницы access получают через refresh, при `401` пробуют refresh и повторяют исходный запрос один раз. Если refresh недействителен, возвращаются к экрану входа и создают нового гостя с согласием.

Затем фронтенд вызывает `POST /api/quiz/sessions/{id}/join` или `POST /api/interactive-video/sessions/{id}/join` без тела. Они используют текущего User, не создают учётные записи и не выдают токены. В викторине один User получает одного GameSessionParticipant на сессию, повторный join не расходует место; лимит проверяется в той же транзакции под блокировкой сессии. В видео отдельной таблицы участников нет, `participant_id` в ответе — ID User. Каждый успешный join, включая повторный, атомарно увеличивает `participant_count` сессии; он возвращается в `voting_point.participant_count`. Уникальность и наличие онлайн-соединения не проверяются.

`POST /quiz/sessions/{id}/team/{team_id}/join` не требует тела; `POST /quiz/sessions/{id}/answer` принимает только `answer` и `is_final`. Сервис находит участника по сессии и User.id, без вступления отвечает `403`. Чужой `participant_id` нельзя передать в ответе. `GET /interactive-video/sessions/{id}/voting` не требует participant_id, а `/vote` принимает только branch_id; оба используют User.id.

Все REST-маршруты `app/api/quiz/sessions.py` проверяют токен через общую точку `app/core/auth.py`. Управление — staff ADMIN/OPERATOR; `/led/next` — активное устройство, которому принадлежит сессия; чтение состояния и результатов — сотрудник, участник или устройство этой сессии. ID в перемещении участника/назначении капитана сохраняется как цель действия оператора. В видео пользовательские join/vote/voting используют User; запуск (`POST /interactive-video/sessions`) и остановка (`POST /interactive-video/sessions/{id}/stop`) доступны только сотрудникам ADMIN/OPERATOR, получение состояния доступно оператору или устройству этой сессии; `/advance` — только устройству этой сессии. Получение активной анкеты `/feedback/surveys/type/{type}` требует device-токен активного LED-устройства. WebSocket проверяет query token и доступ к игровой сессии до accept, без дальнейшей перепроверки.

Личные аватары (`GET /me/avatars`, `GET/DELETE /me/avatars/{avatar_id}`) и история согласий (`GET /consents/acceptances`) используют User из access-токена. Ответы на анкеты принимаются также по Device JWT с ролью 4 и заголовком X-Device-Connection-Id; user_id в JSON запрещён. Чужие аватары недоступны (404). Создание аватара `POST /users/avatars` требует Device JWT с ролью 2 и действующий идентификатор подключения; владелец определяется по Redis.

## Доступ сотрудников

Общие зависимости в `app/core/auth.py` проверяют актуальную роль StaffUser из БД. `require_staff_roles` сначала разрешает ADMIN, затем проверяет допустимые роли. Есть отдельные проверки оператора, редактора контента, аналитика и совместного доступа к чтению.

| Запросы | Доступ помимо ADMIN |
|---|---|
| Управление устройствами `/cms/devices` | OPERATOR |
| Изменение вопросов, шаблонов, настроек викторины, видеосценариев, анкет, справочников и согласий | CONTENT_EDITOR |
| Чтение CMS вопросов, шаблонов, настроек викторины и видеосценариев | CONTENT_EDITOR, OPERATOR |
| Чтение каталога CMS ПрофСтарта | CONTENT_EDITOR, OPERATOR |
| Изменение типов, тестов, групп, вопросов, вариантов и связей профессий ПрофСтарта; публикация и проверка состава | CONTENT_EDITOR |
| Просмотр и прерывание сессий ПрофСтарта `/cms/profstart/sessions` | OPERATOR |
| Создание, замена и удаление аватаров профессий | CONTENT_EDITOR |
| Все видеосценарии `/interactive-video/scenarios` | OPERATOR или активное устройство с ролью QUIZ_VIDEO (1) |
| Сценарии видеосессии `/interactive-video/sessions/{id}/scenarios` | OPERATOR или активное устройство; проверяется только токен и роль |
| Чтение CMS анкет | CONTENT_EDITOR, ANALYST |
| Ответы на анкеты `/cms/surveys/responses` | ANALYST |
| Активный показ `/interactive-video/sessions/active` | OPERATOR или активное устройство; LED получает только показ своего устройства |

Публичное чтение справочников и текстов согласий сохраняется. Чтение аватаров профессий требует действующий токен User, StaffUser или Device. Отсутствующий/недействительный staff-токен возвращает 401, неподходящая роль — 403. Сокеты используют JWT в query token; проверка выполняется только при подключении.

ПрофСтарт: возрастные группы, каталог и карточка активного теста доступны User или активному Device с ролью 3. Без X-Device-Connection-Id каталог устройства не персонализируется; с заголовком учитывает историю пользователя из QR-привязки. Прохождение, результаты, история и `/users/me/recommendations` принимают User JWT либо Device JWT с ролью 3 и обязательным X-Device-Connection-Id. Архивная карточка доступна владельцу своей сессии; staff-токен личного доступа не даёт.

## Отложенные задачи

- Подключить общие зависимости к остальным REST-маршрутам и проверки владельца ресурсов. Сейчас они глобально не защищены.
- Передачу JWT в query WebSocket впоследствии можно заменить другой схемой без изменения игровых событий.
- API смены роли и политика сессий при её изменении; смена/восстановление пароля и email.
- Объединение истории гостя и существующего OAuth-аккаунта; привязка нескольких провайдеров к одному пользователю.
- Политика ограничения попыток входа.
- TODO: периодическая очистка истёкших/отозванных auth_sessions и связанных auth_refresh_tokens небольшими порциями после согласованного срока хранения. Использованные refresh-токены действующих сессий сохранять для обнаружения повторного использования. Пользователей и историю участия не удалять.

См. [идентификацию](identification.md), [пользователей](../entities/users.md), [согласия](../entities/consent.md). ## Группы доступа устройств

Устройство может иметь несколько числовых ролей в `device_roles`. При создании обязателен непустой список; `PUT /cms/devices/{device_id}/roles` полностью заменяет его и требует staff admin/operator. В JWT роли не записываются: общая аутентификация читает актуальные назначения из БД, а зависимости маршрутов проверяют нужную группу. Неверный токен или неактивное устройство — 401; отсутствующая роль модуля — 403.

| Роль | Device-маршруты |
|------|-----------------|
| 1 — викторина и профессии в действии | Чтение состояния и результатов викторины, LED-продвижение; активная видеосессия, состояние, сценарии и advance |
| 2 — аватар | Чтение шаблонов аватаров профессий, создание пользовательского аватара |
| 3 — ПрофСтарт | Возрастные группы, каталог и карточка доступного теста |
| 4 — обратная связь | Получение активной анкеты по типу type |

Проверки User и StaffUser сохраняются. Группа устройства не заменяет проверку принадлежности игровой сессии там, где она уже реализована. Личные результаты и рекомендации по-прежнему доступны только владельцу User. Существующим устройствам seed назначает все четыре группы; оператор затем может ограничить их через CMS.


## Подключение пользователя к устройству через QR

Привязка краткосрочная и хранится только в Redis. Device JWT остаётся на устройстве,
User JWT и refresh-cookie — на телефоне. Новые токены и таблицы для привязки не создаются.
При каждом подтверждении QR создаётся случайный connection_id, включая повторное
подключение того же пользователя. Этот идентификатор используется вместе с Device JWT.

| Запрос | Авторизация | Назначение |
|---|---|---|
| `POST /api/device/auth/qr` | Device JWT | Создать код для QR; ответ 201 |
| `GET /api/device/auth/qr/{code}` | Код QR | Сообщить устройству о переходе и перенаправить на фронтенд; ответ 302 |
| `WS /api/device/auth/ws?token=...` | Device JWT | Получать события открытия QR и подтверждения привязки |
| `POST /api/device/auth/confirm` | User JWT | Подтвердить с телефона: `{"code": "..."}` |
| `GET /api/device/auth/user` | Device JWT | Получить User, connection_id и expires_at |
| `DELETE /api/device/auth/user` | Device JWT; для текущего подключения — X-Device-Connection-Id | Завершить подключение; ответ 204 |

1. Устройство подключает `/api/device/auth/ws?token=<device_jwt>`, затем создаёт QR.
   Сервер определяет устройство по Device JWT и возвращает code и expires_at.
   Фронтенд собирает backend-ссылку `/api/device/auth/qr/{code}` из адреса API
   и полученного кода, затем отображает её QR.
   Код действует 2 минуты; новый QR аннулирует предыдущий неподтверждённый код.
2. Телефон открывает backend-ссылку QR. Backend проверяет актуальность кода и активность устройства,
   отправляет `{"type":"qr_opened","code":"..."}` в его сокет и возвращает 302 на
   DEVICE_AUTH_FRONTEND_URL с fragment `#code=...`. Повторное открытие повторяет событие,
   но не погашает код и не продлевает срок. Неверный/истёкший/заменённый код — 410.
   Мобильный фронтенд сохраняет код, выполняет OAuth или гостевой вход
   и после подтверждения посетителем вызывает `/confirm`.
   user_id и device_id в теле не принимаются.
3. Redis атомарно погашает код и создаёт привязку с новым connection_id. После успеха
   сервис вызывает отправку `{"type":"user_connected","code":"..."}` в сокет устройства. Повторное
   подтверждение, неизвестный, заменённый или истёкший код возвращает 410.
   Занятое устройство возвращает 409; сначала нужно завершить прежнее подключение.
4. Фронтенд устройства ожидает события сокета без периодического опроса `/user`.
   Событие qr_opened сообщает о переходе по QR; после user_connected устройство
   запрашивает `/user`, чтобы получить профиль и connection_id. При подключении
   и переподключении сокета также нужно прочитать `/user`, поскольку события не сохраняются.
   Фронт сверяет code события с текущим QR и игнорирует уведомления о прежнем коде.
   Ответ содержит user (id, is_guest, first_name, last_name, avatar_url), connection_id
   и expires_at; без подключения все три поля null. Email, JWT и auth_session_id не выдаются.
5. Подключение действует до часа с момента подтверждения, без продления при чтении состояния.
   Срок ограничивается также сроком AuthSession и гостевого аккаунта. Каждый личный запрос
   проверяет идентификатор подключения, актуальный User и AuthSession. Logout на телефоне,
   деактивация User или истечение сессии прекращают доступ при следующем запросе.
   Истечение access JWT телефона само по себе не завершает привязку: проверяется AuthSession.
6. `DELETE /user` с текущим идентификатором атомарно удаляет привязку и её ожидающий QR.
   Без заголовка при активном подключении — 422; чужой или устаревший идентификатор — 403.
   Повтор с прежним ID при отсутствии подключения возвращает 204 и сохраняет новый
   неподтверждённый QR. Без ID и без подключения можно отменить ожидающий QR.
   Телефон остаётся авторизованным и может подключить другое устройство.

| Ключ Redis | Значение |
|---|---|
| `device-auth:qr:{sha256(code)}` | ID устройства; TTL QR |
| `device-auth:pending:{device_id}` | Ключ текущего QR; TTL QR |
| `device-auth:user:{device_id}` | connection_id, user_id, auth_session_id, expires_at; TTL подключения |

Универсальная проверка `get_current_device_user` получает устройство из Device JWT,
сверяет X-Device-Connection-Id с текущей Redis-привязкой и возвращает её пользователя.
Клиент не передаёт user_id. Роль модуля проверяется отдельно.

| Операции | Роль устройства | Идентификатор подключения |
|---|---|---|
| Создание аватара `POST /users/avatars` | 2 | Обязателен |
| ПрофСтарт: старт, состояние, вопрос, ответ, прерывание, результаты и история | 3 | Обязателен |
| Общие рекомендации `GET /users/me/recommendations` | 3 | Обязателен |
| Отправка анкеты `POST /feedback/surveys/{survey_id}/respond` | 4 | Обязателен |

ПрофСтарт и отправка анкеты сохраняют вход по User JWT: заголовок не требуется,
владелец определяется по токену. Отсутствующий заголовок для личной операции Device JWT — 422,
неподходящая роль, отсутствие привязки или устаревший connection_id — 403.
Чужая сессия ПрофСтарта по-прежнему возвращает 404. В каталоге и карточке теста заголовок
необязателен: без него устройство читает активные версии без персонализации;
с ним учитывается история пользователя, включая доступ к своей архивной версии.
Остальные личные маршруты сохраняют пользовательскую авторизацию.

Пользователь закрепляется за запросом после проверки подключения и передаётся в сервисы
и фоновые задачи как конкретный User/ID. Уже допущенный запрос может завершиться для прежнего
пользователя; он не переключается на следующего. Запоздавший запрос со старым ID отклоняется.
Фронтенд фиксирует connection_id при начале действия и сохраняет его для повторов;
не подставляет новый ID в незавершённую операцию предыдущего посетителя.

Настройки API: DEVICE_AUTH_QR_TTL_SECONDS=120, DEVICE_AUTH_USER_TTL_SECONDS=3600,
DEVICE_AUTH_FRONTEND_URL=http://localhost:5173/device/auth. Адрес мобильной страницы
должен быть доступен с телефона; его origin включается в AUTH_ALLOWED_ORIGINS.
Фронтенд использует внешний адрес API при формировании ссылки QR, извлекает и сохраняет
код на время OAuth, выполняет подтверждение и получает профиль после события.
События отправляются обычным `manager.broadcast(device_id, type, code)` в текущем
процессе API, как в двух игровых сокетах. Redis хранит коды и привязки пользователей.
Для доставки уведомления HTTP-запрос и сокет должны обрабатываться одним процессом.
Сокет доступен только активному Device; User/StaffUser отклоняются. Авторизация и Origin
проверяются только при подключении; после закрытия соединение удаляется из менеджера.
Потеря Redis-состояния требует повторного сканирования. Привязки старого формата без
connection_id не используются и требуют нового подтверждения QR.


## Авторизация WebSocket

Каналы викторины и видео принимают `?token=<jwt>` и используют ту же проверку User,
Device и StaffUser, что REST. Пользователь передаёт access JWT, устройство — Device JWT.
Для Device проверяются роль 1 и принадлежность сессии; QR-привязка посетителя не требуется.
Сотрудник в видео должен быть admin/operator; в викторине разрешено чтение активному StaffUser.
User в викторине должен быть участником; в видео факт join отдельного пользователя не сохраняется и не проверяется. Хранится только общий счётчик успешных join; голосование без join его не увеличивает.

Авторизация и Origin проверяются до accept и включения в рассылку. БД закрывается сразу
после проверки. Дальнейшей проверки токена/ролей и автоматического отключения при их отзыве нет;
новое подключение требует актуальные права. JWT убирается из локального URL логирования Uvicorn.
Контракт, ограничения и примеры описаны в [WebSocket API](../api/websocket.md).
