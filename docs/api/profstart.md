# ПрофСтарт — API

## Возрастные группы

GET `/profstart/age-groups` (Bearer) и GET `/cms/profstart/age-groups` возвращают справочник `age_groups`: массив объектов `{id, name, min_age, max_age}`, порядок id ASC. По умолчанию — 12–14 и 15–17 лет, границы включительно.

`age_group_ids` хранится в JSON-поле теста как массив ID справочника. Неизвестные или повторяющиеся ID при создании/изменении теста — 422. Неизвестная `age_group_id` в каталоге или при старте — 422, включая тесты без возрастных ограничений. Выбранный ID в сессии защищён FK на справочник. В ответе справочника `min_age` и `max_age` могут быть null — соответствующая граница отсутствует.

Контракт расширяемого каталога типов; итоговый расчёт поддерживает solomin, holland, dellinger. Все URL ниже имеют префикс /api. [OpenAPI](openapi.yaml) · [Сущности](../entities/test.md) · [Методики](../subsystems/profstart/methods.md).

## Общие правила

test_type_id — тип, test_id — версия. Все ID integer int64; в CMS-карточке test_code_type содержит код любого типа; в результатах и пользовательском контуре — только solomin, holland или dellinger. Во всех вопросах type=single_choice; ответ — один answer_option_id.

Контекст владельца определяется сервером по пользовательскому Bearer-токену, включая гостя. Клиент не присылает user_id при старте или ответе. Карточка, прерывание и результат чужой сессии — 404; отсутствие контекста — 401. Маршруты /question и /answer выбирают только собственную сессию in_progress; ID сессии не передаётся, при её отсутствии — 409. CMS-маршруты следуют существующей архитектуре CMS проекта: отдельная проверка токена и административных прав в backend пока отсутствует.

## CMS

Типы можно добавлять через POST /cms/profstart/test-types. code — уникальная строка латиницей в нижнем регистре, цифрами и подчёркиванием, начинается с буквы (1–64 символа). PATCH меняет name и description, в том числе при наличии активного теста. Код дополнительного типа можно изменить только без связанных тестов; коды solomin, holland, dellinger фиксированы. Недопустимая смена кода — 409; дубликат — 409. DELETE типа с активным тестом запрещён: 409; ссылки остальных тестов также защищены FK, каскадного удаления истории нет. Проверка удаления и активация теста согласованы атомарно. Тип без связанных тестов удаляется с 204.

```json
{"code":"new_type","name":"Новый тип теста","description":"Описание"}
```

Дополнительные типы можно наполнить и активировать в CMS. Пользовательское прохождение, результаты и рекомендации доступны только для solomin, holland и dellinger.

Влияние на общий подбор задаётся в profstart_test_types.recommendation_weight_percent: целый процент 0–100, стандарт solomin=40, holland=40, dellinger=20. Сумма весов поддерживаемых типов — ровно 100; 0 отключает влияние типа, сохраняя возможность отдельного прохождения. У новых типов без алгоритма вес по умолчанию 0 и положительное значение запрещено: 422.

Проценты доступны в карточке и каталоге типов. Перераспределение сохраняется атомарным PUT /cms/profstart/test-types/recommendation-weights с полным набором solomin/holland/dellinger. PATCH одного типа также проверяет итоговую сумму; нарушение — 422. Для переноса процента между типами используется PUT всей тройки. Настройка изменяется и при активных тестах; сохранённые результаты отдельных тестов остаются прежними, общий подбор использует текущие веса. Тип с ненулевым весом удалить нельзя: 409; сначала требуется перераспределить проценты.

```json
{"solomin":40,"holland":40,"dellinger":20}
```

PUT возвращает обновлённые записи TestType с recommendation_weight_percent; фиксированный URL регистрируется до /test-types/{test_type_id}.

Тест имеет status=1 (draft), active или archived. Черновик существует только у теста: status=1 (draft), published_at=null. У групп/вопросов нет отдельных состояний или методов публикации. Вопросы и варианты редактируются только у draft. Группы типа и связи профессий редактируются независимо от статуса версии, в том числе active/archived; изменения учитываются только в новых результатах.

Создание теста любого существующего типа назначает номер версии, status=1 (draft) и published_at=null. /validate возвращает 200 с valid=false и errors для неполного состава. /publish проверяет draft, переводит его в active и заполняет published_at; неполный банк — 422. Для Соломина требуется ровно 42 вопроса: по 3 на каждую из 7 групп и блоков want/can; общий максимум — 18 на группу. scale_maxima возвращает по одному объекту group_id/max_score на группу, без axis. Для Голланда — ровно 15 вопросов, максимум 15; для Деллингер — один вопрос. Для нового типа проверяется общая целостность, scale_maxima=[]; алгоритм расчёта не появляется автоматически.

Не более одного active на test_type_id. /publish атомарно архивирует предыдущий active и активирует draft; конкурентные публикации согласованы блокировкой типа и частичным уникальным индексом. /archive переводит active в archived без замены. Повтор /publish для active и /archive для archived возвращает прежнюю запись; /publish для archived и /archive для draft — 409. /copy любой версии создаёт новый draft с собственными ID вопросов и вариантов; группы типа и связи профессий общие. Начатые сессии продолжают и завершают прежнюю версию после архивирования. published_at сохраняет дату первой активации у active/archived.

Основные группы поддерживаемых типов нельзя удалить или изменить их code/category: 409. Добавление кода вне фиксированного набора 7/6/5 или неверной категории — 422; дубликат code внутри типа — 409. У дополнительных типов группы задаются CMS; код и категория группы с вариантами или результатами защищены от изменения (409). Удаление группы с вариантами, результатами или профессиями — 409. Название, описание и связи профессий доступны для редактирования независимо от статуса версии. Связь профессии хранит test_code_type + group_code; при разрешённой смене кода группы дополнительного типа составной FK обновляет связи каскадно. CMS проверяет полноту пар subject/labor Соломина через /validate и при /publish. Завершение сессии проверяет структуру банка без требования полноты связей профессий; профессии с неполной парой исключаются из новых рекомендаций, а баллы всех семи групп сохраняются. Если полных подходящих пар нет, professions=[]. Сохранённые ранее рекомендации не меняются. Удаление вопроса удаляет варианты; отвязка профессии не удаляет Profession. /questions/order принимает полный массив question_ids без повторов и назначает порядок 1..N атомарно.

Вложенные ID в URL проверяются как цепочка принадлежности: test_code_type → group_id → profession_id и test_id → question_id → option_id. Чужой ресурс в этой цепочке — 404; group_id в теле варианта другого типа — 422. Изменения вопросов и вариантов согласованы с публикацией и разрешены только в draft. /copy создаёт новые вопросы и варианты, сохраняя group_id и media_id. Группы и связи профессий остаются общими для типа.

### Вопрос и вариант

Полные тексты, варианты и ключи начального состава представлены в [банке вопросов](../subsystems/profstart/questions/index.md).

Создание и PATCH вопросов/вариантов принимают multipart/form-data. Каждое поле — отдельная часть формы, а не JSON-тело. Пример полей вопроса без вложения:

```text
type=single_choice
axis=want
text=Мне интересно помогать человеку освоить то, что у него пока не получается.
order=1
```

Поля варианта Соломина:

```text
text=3 — Полностью согласен
value=3
order=4
group_id=21
weight=3
```

Файл передаётся бинарной частью file; необязательное превью — file_preview (JPEG, PNG, WebP или GIF), название/описание нового файла — file_title/file_description. Для видео без превью сервер извлекает первый кадр; для остальных файлов автоматического превью нет. file_preview без нового file — 422. Без нового file при PATCH прежний файл и его метаданные сохраняются; file_title/file_description применяются только к новому вложению. media_id не принимается. У Голланда и Деллингер value не передаётся, в ответе value=null.

CMS и пользовательский API возвращают в вопросах/вариантах file: объект url, preview_url, mime_type, title, description либо null. Подписанные ссылки действуют 24 часа; повторное чтение ресурса выдаёт свежие ссылки. В БД остаётся внутренний media_id, в том числе при /copy. Файл и сущность сохраняются в одной транзакции, старые файлы сохраняются для копий и истории. [Файлы](../entities/files.md).

group_id и weight — непосредственные поля варианта, изменяются его обычным PATCH. Блок определяется вопросом; want и can Соломина суммируются по группе. У Соломина четыре варианта с весами 0–3 и равным value; у Голланда шесть действий с весом 1; у Деллингер пять изображений с весом 1. Тип вопроса одинаков. Группа должна принадлежать тому же типу теста.

Связь с профессией:

```json
{"profession_id":17,"coefficient":1}
```

Профессии Соломина необходимы связи subject и labor в одном тесте. Все фигуры связываются с профессиями одинаково. Если связей нет, рекомендаций для группы нет.

|---|---|---|

| POST | `/profstart/sessions` | Начать отдельное прохождение |
| GET | `/profstart/sessions/{id}` | Состояние своего прохождения |
| GET | `/profstart/question` | Следующий неотвеченный вопрос текущей сессии |
| POST | `/profstart/answer` | Сохранить ответ в текущей сессии |
| POST | `/profstart/sessions/{id}/abandon` | Прервать без результата |
| GET | `/profstart/sessions/{id}/result` | Сохранённый результат своей сессии |
| GET | `/profstart/me/sessions` | Список своих сессий с прогрессом |

| GET | `/profstart/me/results` | История своих результатов |

/tests возвращает только active-тесты кодов solomin, holland, dellinger, которые пользователь ещё не завершил, без ключей. Новые типы без алгоритма в пользовательский каталог не входят; прямое получение инструкции или старт — 422, без создания сессии. Старт неактивного теста — 409. age_group_id фильтрует доступность, test_type_id выбирает методику. Без возрастного фильтра возвращаются все доступные типы, возраст проверяется при старте.

```json
{"test_id":12,"age_group_id":2}
```

GET /profstart/tests/{test_id} возвращает status карточки. Активная карточка доступна для инструкции; архивная — только владельцу существующей сессии этого test_id в любом статусе. Название теста для истории читается из этой карточки. Draft и архивная версия без своей сессии — 409; неизвестный ID — 404. Просмотр архивной карточки не разрешает новый старт.

POST /profstart/sessions допускает только одну сессию со status=1 (in_progress) на пользователя среди всех типов и версий тестов. При наличии незавершённого прохождения новый старт возвращает 409 с detail «У пользователя уже есть незавершённое прохождение», включая повторный старт того же теста и прохождение архивной версии. После abandoned можно начать новую попытку. После completed доступны другие ещё не завершённые типы; повторный старт завершённого типа, включая другую версию, — 409 с detail «Тест этого типа уже пройден».

Если age_group_ids теста непустой, age_group_id обязателен и входит в список. Для теста без возрастного ограничения достаточно test_id. Источник и тип интерфейса не передаются.

Сессия содержит test_id, test_type_id, test_code_type, test_version, user_id, age_group_id, status, прогресс, принятые ответы, next_question_id, started_at, completed_at и result_id. Для закрытой сессии next_question_id=null. При прерывании status=3 (abandoned), completed_at=null; отдельной даты прерывания нет.

GET /profstart/me/sessions возвращает `{items, total, limit, offset}` только для текущего пользователя, включая все статусы. Необязательный фильтр status принимает 1, 2 или 3; limit — 1–100 (по умолчанию 50), offset — от 0. Порядок started_at DESC, id DESC. Элементы содержат тот же прогресс и ответы, что карточка сессии. GET /profstart/me/sessions/active возвращает единственную сессию in_progress, включая архивную версию теста, или 200 с JSON null, если её нет.

GET /profstart/question выдаёт один объект: первый неотвеченный вопрос по порядку закреплённой версии собственной сессии in_progress. Сессию сервер находит по Bearer-токену; ID сессии не передаётся. В вариантах нет group_id/weight. Повтор GET не меняет прогресс; до сохранения ответа возвращается тот же вопрос. После успешного /answer клиент запрашивает следующий через тот же URL. Если in_progress нет, включая состояние после completed/abandoned, возвращается 409.

Числа шкалы и картинки — представление одного single_choice. Картинки передаются объектом file с подписанными ссылками существующего File API.

```json
{"answer_option_id":404}
```

POST /profstart/answer требует только answer_option_id. question_id необязателен: если отсутствует или null, сервер берёт первый неотвеченный вопрос, как в GET /profstart/question. ID сессии не передаётся. Сервис находит собственную in_progress и блокирует её в транзакции до выбора вопроса и сохранения ответа. При явном question_id нельзя пропустить предыдущие вопросы: 409. При автоматическом выборе вариант другого или последующего вопроса — 422, без продвижения. Пока сессия in_progress, повтор уже принятого варианта, включая запрос без question_id, возвращает сохранённый ответ и текущий прогресс без повторного начисления и продвижения. Другой вариант уже отвеченного вопроса при явном question_id — 409. При отсутствии собственной in_progress — 409.

Последний ответ автоматически завершает прохождение: /answer атомарно сохраняет ответ, результат, показатели групп и рекомендации и устанавливает status=2 (completed). Подтверждение содержит session_id и текущий status: 1 — in_progress, 2 — completed. Результат в ответ /answer не включается: после status=2 клиент вызывает GET /sessions/{id}/result с session_id из подтверждения. При ошибке расчёта последний ответ и результат откатываются вместе. Повтор сохраняет answered_at только в in_progress; после completed/abandoned и при отсутствии in_progress — 409. При двух одновременных отправках последнего ответа один запрос завершает сессию, второй получает 409; результат создаётся один раз. Сохранённый результат завершённой сессии не меняется. next_question_id=null после completed. /abandon прерывает in_progress без результата; повтор abandoned допустим, а /abandon после completed — 409. После восстановления соединения клиент читает /me/sessions/active, а результат — через /sessions/{id}/result.

Результат содержит id, session_id, test_id, test_type_id, user_id, test_code_type, test_version, age_group_id, полноту, дату, scores и professions. Название читается из ресурса теста при необходимости, не дублируется в результате.

scores — все 7/6/5 показателей, включая нули: группа, category, raw_score, max_score, normalized_score, rank, is_leading. У Соломина raw_score суммирует оба блока want и can, max_score=18; axis в scores и reasons не передаётся. professions — уникальные профессии, score/position и reasons с группами, коэффициентами и числовыми вкладами. [Формулы](../subsystems/profstart/results.md). Дополнительные признаки качества не сохраняются.

Таймаут экрана задаётся клиентом киоска. Скрытие не удаляет историю; после авторизации гостя данные остаются у того же User.

## Общий подбор профессий

Основной маршрут GET `/users/me/recommendations` возвращает сохранённый общий профиль пользователя: максимум три профессии, источники, текущие и эффективные веса. До первого завершённого теста возвращается JSON null. [Контракт общего профиля](user-recommendations.md).

GET `/profstart/me/recommendations` сохраняется как совместимый маршрут. Ответ: calculated_at, is_complete, available_weight_percent, weights, results, missing_test_types, professions. results содержит по одному завершённому результату каждого типа с положительным весом; каждый тип можно завершить один раз. professions содержит profession_id/name, score, position и contributions: test_type_id, test_code_type, result_id, recommendation_weight_percent, effective_weight_percent, test_score, contribution. Без результатов — пустые results и professions, available_weight_percent=0, is_complete=false.

Последний ответ атомарно добавляет источник и обновляет профиль. Изменение весов CMS пересчитывает общий профиль по сохранённым источникам; исторические результаты, показатели и коэффициенты источников не меняются. Для общего подбора используются все группы с положительным вкладом, включая неведущие; Соломину нужна полная положительная пара subject/labor. При неполном наборе веса доступных источников нормируются. Пройденный источник без данной профессии участвует с нулевым вкладом. Нулевой вес отключает влияние, но источник сохраняется. Порядок профессий: score DESC, profession_id ASC; максимум три, без случайного дополнения. [Формулы](../subsystems/profstart/results.md#общий-подбор-по-трём-тестам).

## Списки и фильтры

Списки используют limit (50 по умолчанию, максимум 100), offset (0 по умолчанию). Ответ: items, total, limit, offset. Вопросы/варианты: order ASC, id ASC; группы: id ASC; связи: profession_id ASC; тесты и результаты: created_at DESC, id DESC.

CMS-список тестов фильтруется по test_type_id и status=1 (draft)/active/archived. Каталог типов GET /cms/profstart/test-types возвращает массив всех типов, включая новые, в порядке id ASC, без пагинации. Остальные CMS-списки и история используют описанную пагинацию.

История владельца фильтруется по test_type_id, test_id, date_from и date_to; произвольный user_id не принимает. Несоответствие test_id и test_type_id — 422. Даты ISO 8601 с часовым поясом; интервал [date_from,date_to), неверный интервал — 422. Период выбирает created_at результата; фильтры AND.

Результаты содержат ровно 7/6/5 уникальных group_id; пустой scores не допускается. Для completed обязательны полный набор ответов, completed_at и result_id. У in_progress/abandoned оба поля null; answered_count не превышает question_count. Согласованность массива answers, порядка и next_question_id проверяется сервером.

## Согласованность

Проверки владельца, ссылки на версию, статуса сессии, активности теста при старте и уникальности выполняются атомарно. Ошибка расчёта откатывает завершение: completed без результата не допускается. Ошибки оформляются стандартным HTTPException: поле detail содержит сообщение или список ошибок состава теста. FastAPI возвращает ошибки типов и обязательных полей в detail со стандартными loc, msg и type. Конфликт — 409, неверные параметры/ключ — 422.

Неизвестные query-параметры игнорируются, как в остальных разделах API: переданный user_id не меняет владельца. В PATCH null необязательных полей с обязательным значением игнорируется; для очистки nullable value варианта передайте строку `null` в поле `value` формы multipart/form-data. Отсутствие поля сохраняет прежнее значение.

Поле `status` передаётся числом. Для теста: `1` — draft, `2` — active, `3` — archived; фильтр CMS, например `?status=1`. Для прохождения: `1` — in_progress, `2` — completed, `3` — abandoned. Статус теста меняют `/publish` и `/archive`, статус прохождения — `/answer` после последнего вопроса и `/abandon`.
