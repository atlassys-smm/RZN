# WebSocket API

WebSocket-эндпоинты для получения уведомлений об изменениях в реальном времени.

Клиент подключается к WebSocket, получает уведомление о событии и загружает актуальные данные через REST API.

Все каналы принимают JWT в обязательном query-параметре `token`, без префикса Bearer.
Игровые каналы поддерживают User, включая гостя, Device и StaffUser; каналы QR и сессий устройства — только Device.
До accept проверяются токен и актуальный аккаунт/AuthSession. Для игровых каналов
дополнительно проверяются существование игровой сессии и доступ к ней.
Соединение с PostgreSQL освобождается до регистрации и ожидания сообщений.

| Канал | User | Device | StaffUser |
|---|---|---|---|
| Викторина | Участник этой игры | Активен, роль 1, сессия своего устройства | Активный сотрудник с действующей AuthSession |
| Авторизация QR | Не допускается | Активное устройство из JWT; отдельная роль модуля не требуется | Не допускается |
| Сессии устройства | Не допускается | Активное устройство из JWT; любые роли или без ролей; только свои сессии | Не допускается |
| Видео | Действующая пользовательская авторизация; video join не сохраняет участие | Активен, роль 1, сессия своего устройства | admin/operator с действующей AuthSession |

Если браузер передаёт Origin, он должен входить в AUTH_ALLOWED_ORIGINS.
Клиенты без Origin также поддерживаются. Неверный/отсутствующий токен, запрещённый Origin,
недоступная или отсутствующая сессия отклоняются вызовом `close(code=1008)` до accept;
при HTTP-handshake сервер возвращает 403, поэтому клиент не получает close-frame 1008.

Проверка выполняется только при подключении. Истечение JWT, logout, блокировка аккаунта
или изменение ролей не закрывают уже открытый сокет. При переподключении передайте актуальный
JWT; при необходимости сначала выполните обычный HTTP refresh.
Начальное состояние клиент запрашивает самостоятельно через REST.
Первое сообщение AUTH и отдельный билет не используются.

В рабочем окружении используется wss://. Приложение убирает token из ASGI query_string
до handshake-логирования Uvicorn и после чтения удаляет JWT из состояния соединения.
Внешний reverse proxy видит исходный URL: его access-логи должны скрывать token или не записывать query.

Пример клиента:

```javascript
const socket = new WebSocket(
  `${wsBaseUrl}/api/quiz/sessions/${sessionId}/ws?token=${encodeURIComponent(accessToken)}`
);
```

## Авторизация устройства через QR

Подключение: `ws://host/api/device/auth/ws?token=<device_jwt>`.
Устройство определяется по JWT; ID и connection_id в URL не передаются.

| Событие | Когда отправляется |
|---|---|
| `qr_opened` | Телефон открыл действующую backend-ссылку QR, перед 302 на фронтенд |
| `user_connected` | Успешный `/api/device/auth/confirm` создал привязку пользователя |

Формат: `{"type":"qr_opened","code":"..."}` или `{"type":"user_connected","code":"..."}`.
Клиент сравнивает code с текущим QR. Повторное открытие ссылки повторяет qr_opened;
повтор confirm возвращает 410 и не отправляет user_connected.
Фронтенд ожидает события сокета без периодического опроса. После user_connected
профиль и connection_id читаются через `GET /api/device/auth/user`.
User JWT остаётся на телефоне и в события не включается. Авторизация на телефоне завершается подтверждением
кода через confirm; один OAuth-вход без confirm не подключает устройство.
События отправляются через ConnectionManager в текущем процессе API, как в викторине
и видео, и не сохраняются. Подключите сокет перед созданием QR и прочитайте текущую
привязку через GET /user при подключении и переподключении. Устройство получает только
свои уведомления; после закрытия сокет удаляется из менеджера. Для доставки события
HTTP-запрос и сокет должны обрабатываться одним процессом API.

## Сессии устройства

Подключение: `ws://host/api/device/sessions/ws?token=<device_jwt>`.
Нужен JWT активного устройства. Разрешены любые роли, включая пустой список ролей. Устройство определяется
по JWT и получает только свои события; `device_id` и `session_id` в URL не передаются.
User и StaffUser не допускаются. Правила Origin и проверки токена — как для остальных сокетов.

| Событие | Когда отправляется |
|---|---|
| `session_started` | Создана викторина (`waiting`) или запущен показ интерактивного видео (`active`) |
| `session_finished` | Завершена викторина, видео остановлено оператором или естественно завершён последний сценарий |

```json
{"type":"session_started","payload":{"device_id":1,"session_id":42,"module":"quiz"}}
{"type":"session_finished","payload":{"device_id":1,"session_id":17,"module":"interactive_video"}}
```

`module` принимает `quiz` или `interactive_video`. ID сессии относится к указанному модулю;
числовые ID сессий разных модулей могут совпадать. События отправляются после сохранения
изменения. Переход викторины из `waiting` в `active` не повторяет `session_started`.
Повторное завершение не отправляет событие повторно. В существующих сокетах отдельных
сессий формат сообщений сохраняется.

Подключите этот сокет перед запуском оператором сессии. Начальное состояние и пропущенные
события не отправляются. При подключении и переподключении запросите
`GET /api/quiz/sessions/active?device_id=<id>` и `GET /api/interactive-video/sessions/active`.
После уведомления читайте состояние нужного модуля через REST и подключайтесь к его сокету.
Рассылка, как в остальных каналах, работает в текущем процессе API; запрос и сокет должны
обрабатываться одним процессом. Проверка доступа выполняется при подключении;
БД освобождается до ожидания сообщений. Отключённые соединения удаляются из менеджера.

## Викторина

До раскрытия ответа REST-состояние не содержит `answer_key` вопроса и `is_correct` у вариантов ответа.

### Подключение

```
ws://host/api/quiz/sessions/{sessionId}/ws?token=<jwt>
```

### События от сервера

Все сообщения содержат только `type`. Сессия определяется URL подключения;
поле `data`, состояние, таймер, счётчики, идентификаторы участников и команд,
названия команд и правильные ответы по сокету не передаются.

| Событие | Описание |
|---------|----------|
| `session_state` | Изменилось игровое состояние |
| `participant_joined` | Участник вошёл в сессию |
| `participant_team_changed` | Выбор команды или перенос участника оператором |
| `captain_changed` | Назначение капитана, включая первого участника команды |
| `team_renamed` | Изменилось название команды |
| `question_started` | Начался приём ответов |
| `answers_update` | Принят предварительный ответ участника или решающий ответ капитана |
| `all_answered` | Все участники или все непустые команды ответили; приём ответов досрочно закрыт |
| `question_revealed` | Правильный ответ показан |
| `timer_paused` | Таймер на паузе |
| `timer_resumed` | Отсчёт возобновлён |
| `timer_updated` | Добавлено время (в том числе на паузе) |
| `timer_stopped` | Оператор закрыл приём ответов |
| `timer_expired` | Приём ответов закрыт по времени |
| `round_finished` | Показан ответ на последний вопрос раунда или выполнен переход из раунда без раскрытия |
| `session_finished` | Сессия завершена |

После подключения, переподключения и получения любого события клиент запрашивает
`GET /quiz/sessions/active?device_id=...`. Начальный `session_state` сервер не отправляет.
Для обновления состава используются повторяющиеся параметры
`select=teams&select=participants`. Состояние содержит вопрос, правильный ответ после
раскрытия, таймер, счётчики ответов, `round_count` и `current_round_question_count`
(до старта — число вопросов первого раунда), а также `can_start_final_round`.
В текущем вопросе `current_question.revealed` показывает, был ли его ответ раскрыт для игроков.
Флаг одинаков для всех ролей и сбрасывается при запуске нового вопроса.
В `waiting` и `finished` объекта `current_question` нет. Наличие
`correct_answer` у оператора до reveal не меняет этот флаг.
После раскрытия последнего вопроса последнего раунда `can_start_final_round` позволяет оператору
выбрать `/finish` или `/final-round`; если в сессии уже есть финал типа `9`, поле `false`.
Запуск дополнительного финала отправляет обычные `question_started` и `session_state`,
не создавая новую сессию. После финала клиент вызывает `/finish` без повторного выбора.

После завершения сессии `/quiz/sessions/active` возвращает `404`, если другой
незавершённой сессии нет. Состояние завершённой игры и итоговые результаты доступны
по сохранённому ID через `GET /quiz/sessions/{id}` и `GET /quiz/sessions/{id}/results`.
Голосование текущего вопроса запрашивается через `select=answers`:
`GET /quiz/sessions/active?device_id=...&select=answers` или
`GET /quiz/sessions/{id}?select=answers`. Корневое поле `answers` содержит
`participant_answers`, `team_answers` и `option_counts`. User в командной игре
видит голоса своей команды и решающий ответ капитана, StaffUser — все команды,
Device — общие счётчики и статусы команд без содержимого ответов.
Без `select=answers` поле отсутствует; до начала и после завершения игры оно `null`.
Ответ команды берётся из текущего голоса капитана;
`team_answers[].submitted` становится `true`, когда капитан ответил, независимо от `is_final`.
Ответ капитана всегда решающий независимо от `is_final`; повторная отправка отклоняется.
Уведомление `answers_update` остаётся без данных.

Имена участников в REST-состоянии (`name`, `participant_name`) берутся из `users.first_name` и `users.last_name`. Для нового гостя это «Гость users.id». Идентификатор участника и ID пользователя могут отличаться.

После ответа последнего участника индивидуальной игры или ответа капитана последней непустой команды приём ответов автоматически закрывается. Голос капитана всегда решающий, независимо от `is_final`; предварительные голоса остальных участников не завершают командное голосование. Пустые команды не учитываются. После `answers_update` отправляется `all_answered` (только поле `type`), затем применяется та же обработка, что при окончании таймера через `/led/next`: при числовом `auto_reveal_delay` ответ раскрывается и начисляются баллы, при `null` ожидается ручной `reveal` или `skip`. Досрочное закрытие не отправляет `timer_expired` или `timer_stopped`. Дальнейший переход выполняется по существующему сценарию LED, задержки отсчитывает клиент.

В командном режиме `team_answers[].submitted` по-прежнему означает наличие любого ответа текущего капитана; для досрочного закрытия учитываются ответы капитанов; каждый такой ответ считается решающим. Событие `all_answered` отправляется один раз на вопрос; после закрытия новые и повторные ответы отклоняются.

После переноса участника отправляется только `participant_team_changed`, включая случаи автоматической смены капитанов. Клиент по этому событию перечитывает составы и капитанов команд через REST. Повторный перенос в ту же команду не отправляет события.

Уведомления отправляются после сохранения соответствующего изменения.
`session_state` отправляется после смены вопроса, раскрытия ответа,
изменений таймера и завершения сессии, без снимка состояния.

Истечение времени обрабатывается при `POST /quiz/sessions/{id}/led/next`;
фонового таймера рассылки нет. Если `auto_reveal_delay` задан числом, при
обработке истёкшего таймера отправляется `question_revealed`, при `null`
ожидается действие оператора. Задержки отсчитывает клиент перед вызовом API;
сервер не проверяет их сроки и не сохраняет дополнительные временные метки.
После показа ответа клиент ожидает `auto_next_delay` внутри раунда или
`between_rounds_delay` между раундами и вызывает `/led/next`; при `null`
соответствующее автоматическое действие отключено. После ручной остановки
таймера положительный `auto_reveal_delay` отрабатывает клиент через `reveal`,
`0` раскрывает ответ сразу, `null` оставляет показ оператору.
Повторная проверка уже закрытого таймера не отправляет `timer_expired` повторно. После раскрытия
последнего вопроса отправляется `round_finished`, включая последний раунд;
сессию завершает оператор через `/finish`.

Подписка по URL получает все события этой сессии. Фильтрации через клиентское
сообщение `subscribe` нет. Порядок уведомлений между одновременными запросами
не заменяет получение актуального состояния через REST.

### Формат событий

```json
{ "type": "session_state" }
{ "type": "participant_joined" }
{ "type": "participant_team_changed" }
{ "type": "captain_changed" }
{ "type": "team_renamed" }
{ "type": "answers_update" }
{ "type": "all_answered" }
{ "type": "question_started" }
{ "type": "question_revealed" }
{ "type": "timer_paused" }
{ "type": "timer_resumed" }
{ "type": "timer_updated" }
{ "type": "timer_stopped" }
{ "type": "timer_expired" }
{ "type": "round_finished" }
{ "type": "session_finished" }
```

Машиночитаемая схема события — `QuizWebSocketEvent` и расширение
`x-websocket-channels.quiz-session` в исходном OpenAPI.

## Профессии в действии

### Подключение

```
ws://host/api/interactive-video/sessions/{sessionId}/ws?token=<jwt>
```

Подключение регистрируется только после проверки существования сессии и освобождения
соединения с БД. Начальное состояние LED и оператор запрашивают через
`GET /interactive-video/sessions/{id}/state`, мобильный клиент — через
`GET /interactive-video/sessions/{id}/voting?participant_id=...`.

Для поиска активного показа мобильный клиент с User JWT (включая гостя) может
вызвать `GET /api/interactive-video/sessions/active?device_id=...`. Без `device_id`
возвращается любая активная сессия; присоединение к показу и QR-привязка для этого
запроса не требуются. Если активной сессии нет — 404. Права WebSocket и остальных
REST-запросов остаются прежними.

### События от сервера

**Для LED-экрана:**

| Событие | Описание | Что загружать |
|---------|----------|---------------|
| `phase_changed` | Сменилась фаза (playing → voting) | `GET /state` |
| `votes_updated` | Поступил новый голос | `GET /state` |
| `scenario_finished` | Сценарий завершён, переход к следующему | `GET /state` |
| `session_finished` | Показ завершён | — |

**Для мобильного клиента:**

| Событие | Описание | Что загружать |
|---------|----------|---------------|
| `phase_changed` | Сменилась фаза (voting → playing) | `GET /voting` |
| `scenario_finished` | Сценарий завершён | `GET /voting` |
| `session_finished` | Показ завершён | — |

Мобильному клиенту не нужен `votes_updated` — он уже проголосовал и ждёт результат.

### Формат событий

```json
{ "type": "phase_changed" }
{ "type": "votes_updated" }
{ "type": "scenario_finished" }
{ "type": "session_finished" }
```

### Фазы показа

| Фаза | Описание |
|------|----------|
| `playing` | Проигрывание ролика |
| `waiting` | Точка голосования, сбор ответов |
| `result` | Показ результата |

## Пример использования

1. Клиент подключается к WebSocket
2. Загружает начальное состояние через REST API
3. Получает событие `{ "type": "votes_updated" }`
4. Загружает обновлённое состояние через REST API
5. Обновляет отображение


### Файлы в состоянии сессий

В состояниях викторины и интерактивного видео поле `media_url` заменено на
`file`: объект с `url`, `mime_type`, `title`, `description` или `null`, если медиа
нет. `url` — подписанная ссылка со сроком действия 24 часа. В викторине объект
возвращается у вопроса и каждого варианта ответа; в видео — у `current_branch`.
