# Версия 0.10

Дата: 09.10.2026

---

## Авторизация и пользователи

Реализованы отдельные учётные записи сотрудников, гостевой вход посетителей и OAuth Яндекс ID/VK ID. Пользовательские JWT заменены access-токенами с проверкой серверной сессии; права сотрудников и владельцы пользовательских ресурсов проверяются по данным БД.

### Сотрудники

- Добавлена сущность `StaffUser`: имя, фамилия, уникальный email, хеш пароля, роль, статус и время последнего входа. Роли: `1` — admin, `2` — operator, `3` — analyst, `4` — content_editor; статусы: `1` — active, `2` — blocked.
- Вход выполняется по email и паролю. Email нормализуется; пароль хранится через bcrypt с предварительным SHA-256/base64, без обрезания длинных паролей. Неверные данные и блокировка возвращают одинаковый `401`.
- Нового сотрудника создаёт только активный администратор. Повтор email возвращает `409`, недопустимая роль — `422`. Роль для проверки доступа читается из БД, а не из JWT.
- Добавлена интерактивная команда `python -m app.cli.create_admin --email admin@example.org --first-name Admin --last-name User` для первого администратора; пароль запрашивается отдельно.

### Посетители и OAuth

- Гость создаётся на 24 часа с `is_guest=true` и `guest_expires_at`. Требуются `consent_version_id` и `consent_accepted=true`; пользователь, принятие согласия с IP клиента и сессия сохраняются одной транзакцией. Несуществующая версия или отказ от согласия возвращают `422`.
- Сервер проверяет существование версии согласия; её тип, статус, актуальность и дату вступления в силу пока не проверяет. Для получения текста добавлен `GET /api/consents/types/{type_id}/versions/active`.
- OAuth запускается отдельным фронтендом, который проверяет `state` и передаёт одноразовый код в query-параметре `token`. API обменивает код на сервере и получает профиль. Для VK также обязательны `device_id`, `state`, `redirect_uri`; проверяются разрешённый origin redirect URI, возвращённый state и совпадение ID пользователя в токене и профиле.
- Аккаунт определяется парой `(oauth_provider, oauth_provider_id)`, без объединения по email. При отсутствии существующего OAuth-аккаунта действующий гость становится авторизованным с тем же ID и результатами. Если аккаунт уже существует, вход выполняется в него, история гостя остаётся отдельно. Истёкший гость не привязывается; смена связанного OAuth-аккаунта возвращает `409`.
- После успешной привязки исходная сессия отзывается и создаётся новая на 7 дней. Конкурентные входы одного OAuth-аккаунта сериализуются блокировкой PostgreSQL; ошибки не оставляют частично созданного пользователя или согласия.
- Из профиля сохраняются `first_name`, `last_name`, email, пол, полная дата рождения и ссылка аватара `avatar_url`, если предоставлены. Изменившаяся ссылка аватара обновляется при следующем OAuth-входе; отсутствующие поля и заглушка Яндекса не стирают прежние данные. Сведения о текущем посетителе доступны через `GET /api/user/info`.

### Основные маршруты

| Маршрут | Назначение |
|---------|------------|
| `POST /api/auth/login` | Вход сотрудника; access, ID сотрудника и роль в JSON, refresh в cookie |
| `POST /api/auth/staff` | Создание сотрудника администратором |
| `POST /api/auth/refresh`, `POST /api/auth/logout` | Обновление токенов и выход сотрудника |
| `POST /api/auth/user/guest` | Создание гостя с согласием; access и ID пользователя в JSON, refresh в cookie |
| `GET /api/auth/user/oauth/{provider}` | Вход через `yandex` или `vk`, в том числе привязка действующего гостя |
| `POST /api/auth/user/refresh`, `POST /api/auth/user/logout` | Обновление токенов и выход посетителя |
| `GET /api/user/info` | ID, признак гостя, email, имя, фамилия и URL аватара текущего посетителя |

## Серверные сессии и токены

- Access — JWT со сроком до 30 минут и обязательными `sub`, `type`, `sid`, `iat`, `exp`, `iss`, `aud`; при выдаче добавляется `jti`. Проверяются подпись, тип аккаунта, владелец сессии, её срок и отзыв, актуальный статус аккаунта и срок гостя. Старые пользовательские JWT без серверной сессии больше не подходят.
- Сессия сотрудника или OAuth-пользователя действует 7 дней от входа, гостя — до истечения его 24 часов. Refresh не продлевает абсолютный срок; access также ограничен сроком сессии.
- Refresh — одноразовая случайная строка; в PostgreSQL хранится только SHA-256 хеш и история использования. Ротация блокирует строку сессии и выдаёт новые токены. Повтор использованного refresh отзывает всю эту сессию и возвращает `401`; параллельные вкладки должны координировать обновление.
- Logout отзывает текущую сессию и удаляет cookie (`204`); её access сразу перестаёт проходить проверку, остальные сессии сохраняются. Блокировка аккаунта также запрещает access и refresh.
- Refresh передаётся только через HttpOnly cookie: `staff_refresh` с Path `/api/auth`, `user_refresh` с Path `/api/auth/user`. В JSON возвращаются только access, `token_type=bearer` и `expires_in`; оба вида входа могут одновременно использоваться в браузере.
- Cookie по умолчанию имеют `Secure` и `SameSite=Lax`. Login, гостевой вход, OAuth, refresh и logout требуют доверенный `Origin`, при его отсутствии — `Referer`; неподходящий источник возвращает `403`. Все ответы авторизации и `/api/user/info`, включая ошибки, запрещают кеширование.
- Добавлены `AUTH_COOKIE_SECURE`, `AUTH_COOKIE_SAMESITE`, `AUTH_ALLOWED_ORIGINS`, `AUTH_CONSENT_CODE` и настройки OAuth Яндекс/VK в `.env.example`. CORS использует тот же список origins; `SameSite=None` допускается только с `Secure=true`. Для запросов с refresh-cookie фронтенду нужен `credentials: 'include'`.
- Общие проверки доступа перенесены в `app/core/auth.py`; бизнес-операции, обмен с OAuth-провайдерами и транзакции выделены в `app/services/auth/`. Добавлены зависимости `bcrypt` и `email-validator`.

## Доступ к CMS и пользовательским данным

Администратор имеет доступ ко всем перечисленным операциям; для остальных сотрудников действуют следующие права.

| Операции | Роли помимо admin |
|----------|------------------|
| Управление устройствами `/api/cms/devices` | operator |
| Изменение вопросов, шаблонов и настроек викторины, видеосценариев, анкет, профессий, отраслей, направлений, организаций и согласий | content_editor |
| Чтение CMS вопросов, шаблонов и настроек викторины, видеосценариев | content_editor, operator |
| Чтение CMS анкет | content_editor, analyst |
| Просмотр ответов на анкеты `/api/cms/surveys/responses` | analyst |
| Управление сессиями викторины, запуск и остановка видеопоказов | operator |
| Чтение каталога CMS ПрофСтарта | content_editor, operator |
| Изменение типов, версий, групп, вопросов, вариантов и связей профессий ПрофСтарта; публикация и проверка состава | content_editor |
| Просмотр и прерывание прохождений ПрофСтарта | operator |
| Создание, замена и удаление аватаров профессий | content_editor |
| Чтение сценариев видеосессии | operator или активное устройство |

- Отсутствующий или недействительный токен возвращает `401`, неподходящая роль — `403`. Публичное чтение справочников и текстов согласий сохраняется.
- Личные аватары (`GET /api/me/avatars`, `GET/DELETE /api/me/avatars/{avatar_id}`), история согласий и отправка ответа на анкету используют текущего User из access-токена. Передача `user_id` больше не выбирает владельца; в JSON ответа на анкету это поле запрещено. Чужой аватар возвращает `404`.
- Получение активной анкеты `/api/feedback/surveys/{external_id}` требует токен активного устройства.
- Чтение аватаров профессий требует действующий токен пользователя, сотрудника или устройства; изменения доступны admin/content_editor. Создание пользовательского аватара требует активное устройство с ролью аватара и подтверждённую QR-привязку по X-Device-Connection-Id; маршрут создания — POST /api/users/avatars. Получение сценариев видеосессии доступно admin/operator или активному устройству. Выбор сценариев и обработка файлов сохраняются; владелец нового аватара определяется по Redis-привязке.
- Все 36 операций CMS ПрофСтарта проверяют staff-токен и актуальную роль. Прохождение, история, результаты и общие рекомендации доступны по User JWT либо Device JWT с ролью ПрофСтарта и QR-привязкой по X-Device-Connection-Id; чужая сессия возвращает `404`. Активное устройство может читать возрастные группы и каталог активных тестов без персонализации; для личных данных и своей архивной версии требуется X-Device-Connection-Id и QR-привязка.

## Роли устройств

- Добавлены `device_roles` и числовой enum: 1 — викторина и профессии в действии, 2 — аватар, 3 — ПрофСтарт, 4 — обратная связь. Одно устройство может работать в нескольких модулях; пара device_id/role уникальна.
- Создание устройства требует хотя бы одну роль. `PUT /api/cms/devices/{device_id}/roles` полностью заменяет список и доступен admin/operator; пустые списки, дубли и неизвестные коды отклоняются.
- Device-маршруты проверяют нужную группу по актуальным данным БД; роли не включаются в JWT, обновление действует сразу для существующего токена. Проверки User/StaffUser и принадлежности игровых сессий сохраняются.
- Миграция `0055` создаёт таблицу, отдельный seed `0056` назначает существующим устройствам все четыре роли для сохранения доступа. Новые устройства получают только явно выбранные роли.

## Подключение пользователя к устройству

- Добавлены `/api/device/auth/qr`, `/confirm` и `/user` (GET/DELETE): API выдаёт код и срок действия; фронтенд собирает backend-ссылку для QR. Переход по ссылке уведомляет устройство и перенаправляет на мобильный фронтенд; пользователь подтверждает подключение, панель получает профиль и завершает привязку. Сокет `/api/device/auth/ws` принимает Device JWT и сообщает об открытии QR и успешном подтверждении через менеджер соединений.
- Привязка хранится только в Redis до часа, QR действует две минуты. Коды одноразовые; обновление QR и подтверждение выполняются атомарно. Device JWT остаётся на панели, User JWT — на телефоне.
- Универсальная get_current_device_user проверяет X-Device-Connection-Id и пользовательскую сессию, а владельца получает из Redis. Каждый вход создаёт новый идентификатор; старые запросы не выполняются для следующего посетителя. Она применяется к созданию аватара, прохождению и результатам ПрофСтарта, общим рекомендациям и отправке анкеты; отдельно проверяется роль модуля. user_id из запросов устройства убран; для ПрофСтарта и анкеты вход по User JWT сохраняется. Отключение защищено тем же идентификатором. Истечение срока, logout и деактивация пользователя прекращают доступ. Новые миграции не требуются.

## Изменения игровых контрактов

- `POST /api/quiz/sessions/{id}/join` и `POST /api/interactive-video/sessions/{id}/join` требуют существующий пользовательский access. Они больше не создают гостя и не возвращают токен: вход выполняется заранее через `/api/auth/user/*`.
- В викторине повторный join сохраняет одного участника на User и сессию, не расходуя дополнительное место. Проверка вместимости и добавление участника выполняются под блокировкой сессии.
- Вступление в команду не требует тела; ответ викторины принимает только `answer` и `is_final`. Участник определяется по User из токена; без вступления выбор команды и ответ возвращают `403`, передача чужого `participant_id` в ответе запрещена.
- Чтение состояния и результатов викторины доступно сотруднику, участнику этой игры или её устройству. `select=teams` и `select=participants` сохраняются; ответы команды в состоянии выдаются капитану, определяемому по access-токену, вместо query-параметра `participant_id`.
- Продвижение викторины `/led/next` и видео `/advance` требует токен устройства, которому принадлежит сессия. В видео чтение `/state` и `/active` доступно admin/operator или устройству своей сессии.
- Видео `/voting` больше не требует `participant_id`, `/vote` принимает только `branch_id`; голосующий определяется по User из access. Отдельной таблицы участников видео нет, `participant_id` ответа join равен ID User.
- Временный маршрут выдачи JWT по ID пользователя не подключён. Восстановлены импорты маршрутов видеосценариев и multipart-описания вопросов викторины и анкет при интеграции с ПрофСтартом.

## Авторизация WebSocket

- Сокеты викторины и видео требуют JWT в query token. Поддерживаются User, Device и StaffUser; до accept проверяются аккаунт/сессия и доступ к игровому каналу. Device требуется роль 1 и своё устройство; в викторине User должен быть участником, в видео staff — admin/operator.
- Авторизация выполняется только при подключении, без дальнейшей перепроверки и отключения по истечению JWT. Ошибки отклоняются до handshake; игровые события и получение данных через REST сохраняются.
- JWT убирается из ASGI URL локального логирования Uvicorn. При переданном Origin проверяется AUTH_ALLOWED_ORIGINS; новые таблицы и миграции не нужны.

## Миграции

Миграции авторизации следуют за ПрофСтартом (`0049`), актуальная цепочка — `0050–0054`.

| Ревизия | Изменение |
|---------|-----------|
| `0050` | Замена `users.guest_id` на `is_guest`, перенос прежних статусов в active/deactivated и определение срока гостя; у существующих OAuth-пользователей гостевой срок очищается |
| `0051` | Создание `staff_users` |
| `0052` | Создание `auth_sessions` с одним владельцем — посетителем или сотрудником |
| `0053` | Отдельное создание `auth_refresh_tokens` с хешами и историей использования |
| `0054` | Переименование `users.name` в `first_name` без изменения содержимого, добавление nullable `last_name`; фамилия из старой строки не выделяется |

Прежние номера миграций авторизации `0036–0039` заменены после объединения с `development`; таблицы сотрудников, сессий и refresh-токенов создаются отдельными миграциями. `guest_id` удаляется, ID пользователей и связи с их результатами сохраняются.

Покрыты OAuth для обоих провайдеров, привязка гостя, конфликты аккаунтов, конкурентные входы/refresh, откат транзакций и преобразование прежних пользователей.

## Границы реализации

- Проверка принадлежности устройства при чтении сценариев видеосессии остаётся отдельной задачей.
- Смена ролей через API, смена/восстановление пароля, политика сложности паролей и ограничение попыток входа пока не реализованы.
- Объединение истории гостя с существующим OAuth-аккаунтом и привязка нескольких провайдеров не поддерживаются. Периодическая очистка истёкших/отозванных серверных сессий и refresh-токенов отложена.
