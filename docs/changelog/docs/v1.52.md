## Изменения

### Служебные аккаунты

Новая концепция служебных пользователей для модулей ПрофСтарт и Аватар:

**Поле `users.service_user`** (nullable unique integer):
- Значения 1–5 — служебные аккаунты ПрофСтарта
- Значения 6–10 — служебные аккаунты аватара
- null — обычный пользователь
- Миграция 0099: добавление поля и создание 10 активных аккаунтов

**`POST /api/auth/user/service`** — получение служебного аккаунта:
- Доступ: администратор (Staff JWT) или устройство (Device JWT любой роли)
- `module=1` — ПрофСтарт (service_user 1–5)
- `module=2` — аватар (service_user 6–10)
- Выбор по минимальному `MAX(auth_sessions.created_at)`; не использованные идут первыми
- Блокировки и резервирования пула нет; входы должны быть последовательными
- Ответ 201: `user_id`, `service_user`, `access_token`, `token_type`, `expires_in`
- Refresh в HttpOnly cookie `user_refresh`

**Сброс данных перед выдачей:**
- Профиль, согласия, прохождения и ответы ПрофСтарта
- Источники рекомендаций
- Задания генерации, аватары и собственные файлы
- Общие шаблоны сохраняются
- Auth-сессии отзываются, но сохраняются для порядка выдачи
- Поздний webhook удалённого задания получает 404

**Кеш:**
- Очищается только персональный кеш выбранного аккаунта
- При недоступности Redis — 503, изменения БД откатываются

### Служебный аккаунт для аватара

Работа через существующую привязку к устройству:
- Устройство создаёт QR через `POST /api/device/auth/qr`
- Служебный пользователь подтверждает привязку через `POST /api/device/auth/confirm`
- `POST/GET /api/users/avatar-generations` требуют Device JWT с ролью AVATAR и `X-Device-Connection-Id`
- В задание записывается ID устройства
- Повторная выдача аккаунта отзывает прежнюю auth-сессию и делает старую привязку недействительной

### Обновления API

`GET/PATCH /api/user/info` возвращает `service_user`:
- Номер служебного аккаунта (1–10) или null для обычного пользователя
- Добавлен в обязательные поля `UserInfoResponse`
