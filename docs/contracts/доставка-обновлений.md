# Техническое задание

## Оказание услуг по разработке механизма централизованной доставки, автоматической синхронизации и исполнения обновляемых программных модулей для распределённых терминалов

---

## 1. Цели и основание работ

### 1.1. Наименование закупки

Оказание услуг по разработке механизма централизованной доставки, автоматической синхронизации и исполнения обновляемых программных модулей для распределённых терминалов.

### 1.2. Основание для выполнения работ

В экспозиции Центра занятости населения используется множество разрозненных терминалов: ПАКи, LED-медиаплатформы и другие устройства, объединённые в единую экосистему «ПрофНавигатор». Каждый терминал работает автономно и содержит собственный набор программного обеспечения: клиентские приложения, модули визуализации, конфигурации сценариев, медиаконтент.

При необходимости обновить логику модуля — добавить новый интерактивный виджет, исправить сценарий, обновить карточки профессий или внести изменения в конфигурацию — ручное обновление каждого терминала с внешнего накопителя занимает значительное время и гарантированно приводит к рассинхронизации версий: часть терминалов работает с новой версией, часть — со старой. Это создаёт риски некорректного функционирования, невозможности коллективных сценариев с разных терминалов и затрудняет диагностику.

Кроме того, ручное обновление требует физического доступа к каждому терминалу, что означает остановку его работы на время обновления. В условиях ежедневной эксплуатации экспозиции это приводит к простоям и невозможности оперативного внесения исправлений.

Ситуация дополнительно осложняется тем, что обновления могут касаться как исполняемого кода (исправление ошибок, новая функциональность), так и контента (новые вопросы, карточки профессий, видеоролики). Оба типа обновлений требуют оперативной доставки на все терминалы, но имеют различную периодичность и объём.

### 1.3. Цель работ

Разработка и внедрение системы централизованной доставки обновлений, обеспечивающей автоматическую синхронизацию программного обеспечения компонентов платформы «ПрофНавигатор» на распределённых терминалах из единого управляющего центра.

Администратор публикует изменения в центральном репозитории. После этого каждый терминал самостоятельно, по настроенному расписанию, получает актуальную версию и выполняет сборку обновлённых компонентов.

### 1.4. Ожидаемые результаты

- исключение ручного обновления терминалов и связанного с ним физического доступа к каждому устройству
- обеспечение идентичности программных версий на всех терминалах экосистемы
- сокращение времени доставки обновлений с дней до минут
- возможность оперативного внесения исправлений без остановки работы экспозиции
- полная история всех обновлений с возможностью отката к любой предыдущей версии

## 2. Область применения

### 2.1. Распределённые терминалы

Система доставки обновлений обслуживает программно-аппаратные комплексы экосистемы «ПрофНавигатор».

### 2.2. Место эксплуатации

г. Рязань, ул. Электрозаводская, д. 52.

### 2.3. Архитектурная модель

Система строится по модели «центральный репозиторий — распределённые клиенты»:

- **Центральный репозиторий** — серверный компонент, хранящий исходные коды, артефакты сборки и метаданные обновлений.
- **Клиентский механизм** — компонент на каждом терминале, обеспечивающий периодическое получение изменений из репозитория, сборку актуальных версий компонентов и применение обновлений.

Взаимодействие между компонентами построено по принципу «тянущей доставки»: терминал самостоятельно запрашивает обновления из репозитория, репозиторий не инициирует_PUSH_-доставку на терминалы. Это обеспечивает устойчивость к временной недоступности отдельных терминалов и не требует настройки сетевой связности от репозитория к терминалам.

## 3. Срок выполнения работ

**Срок оказания услуг:** не более **60 календарных дней** с даты заключения контракта.

Работы выполняются в один этап.

## 4. Требования к центральному репозиторию

### 4.1. Хранение и версионирование

- централизованное хранение исходных кодов обновляемых компонентов платформы
- версионирование с фиксацией номера версии, даты публикации и описания изменений
- хранение всех версий для возможности отката к любой предыдущей
- структура репозитория позволяет однозначно определить, какие файлы относятся к какой версии компонента
- репозиторий хранит как исходные коды компонентов, так и конфигурационные файлы, необходимые для сборки
- медиафайлы и крупные ресурсы хранятся с учётом дедупликации: если файл не изменился между версиями, он не дублируется

### 4.2. Управление публикацией

- публикация обновления выполняется через слияние изменений в основную ветку репозитория
- после слияния изменения автоматически становятся доступными для терминалов
- история версий фиксируется средствами репозитория (история коммитов, теги)
- каждый коммит в основной ветке содержит описание внесённых изменений
- для значимых выпусков используются теги с семантической версией (мажорная, минорная, патч)
- основная ветка является защищённой: слияние требует прохождения проверки (code review или автоматические тесты)

### 4.3. Доступ к репозиторию

- терминалы получают доступ к репозиторию по протоколу HTTP/HTTPS
- доступ к репозиторию осуществляется только на чтение — терминалы не вносят изменений в репозиторий, за исключением передачи отчётов о результатах обновления
- репозиторий доступен для всех терминалов одновременно без ограничения количества одновременных подключений
- доступ на запись (для публикации обновлений) ограничен и защищён аутентификацией

### 4.4. Структура репозитория

- репозиторий организован по компонентному принципу: каждый обновляемый компонент платформы имеет собственный каталог
- конфигурационные файлы сборки размещаются в корне репозитория или в каталоге компонента
- общие зависимости и библиотеки вынесены в отдельный каталог, доступный всем компонентам
- структура каталогов документирована и позволяет новому разработчику быстро ориентироваться в коде

### 4.5. Журнал операций репозитория

- репозиторий ведёт журнал всех операций: публикация, слияние, создание тегов
- журнал содержит: дату и время операции, идентификатор инициатора, описание изменений, результат
- журнал доступен для аудита и не может быть модифицирован задним числом

## 5. Требования к клиентскому механизму

### 5.1. Периодическая синхронизация

- терминал периодически обращается к центральному репозиторию для проверки наличия новых версий
- настраиваемое расписание проверки (по умолчанию — не реже одного раза в час)
- синхронизация выполняется в фоновом режиме без влияния на работу основного приложения
- при отсутствии сетевого соединения терминал продолжает работу на текущей версии без ошибок и уведомлений пользователю
- при восстановлении соединения терминал немедленно выполняет внеплановую проверку наличия обновлений
- терминал сравнивает локальную версию с актуальной в репозитории и определяет, требуется ли обновление

### 5.2. Получение и сборка обновлений

- получение изменений из репозитория по протоколу HTTP/HTTPS
- автоматическая сборка актуальных версий клиентских компонентов на терминале
- проверка целостности полученных данных
- применение собранного обновления с минимальным прерыванием работы терминала
- при первой сборке на терминале выполняется установка всех необходимых зависимостей, при последующих обновлениях — только инкрементальные изменения
- загружаются только те файлы, которые изменились между текущей и целевой версией
- процесс сборки изолирован и не влияет на работающие компоненты до момента применения

### 5.3. Откат

- при обнаружении ошибки в обновлённом компоненте — автоматический откат к предыдущей стабильной версии
- возможность принудительного отката по команде администратора
- предыдущая версия сохраняется на терминале до подтверждения успешной работы новой версии
- откат не приводит к потере данных, накопленных терминалом
- критерии автоматического отката: компонент не запускается в течение заданного времени, аварийное завершение при старте, критическая ошибка в журнале
- после успешного отката терминал передаёт отчёт об ошибке и продолжает работу на стабильной версии

### 5.4. Отчётность

- передача отчёта о результате обновления в центральный репозиторий: идентификатор терминала, версия, результат (успешно / ошибка / откат)
- отчёт передаётся при наличии сетевого соединения с репозиторием
- при ошибке отчёт содержит описание ошибки и контекст (этап, на котором произошла ошибка)
- отчёты хранятся в репозитории и доступны для анализа

### 5.5. Влияние на работу терминала

- процесс получения и сборки обновлений не оказывает заметного влияния на производительность основного приложения терминала
- сборка выполняется с низким приоритетом системных ресурсов
- применение обновления не требует перезагрузки терминала или операционной системы
- в случае если сборка занимает значительное время, терминал продолжает работу на текущей версии до завершения сборки
- сетевая активность при загрузке обновлений ограничена, чтобы не создавать нагрузку на общую сеть

### 5.6. Обработка конфликтов и ошибок

- при неудачной загрузке (обрыв соединения, таймаут) терминал повторяет попытку при следующей плановой проверке
- при повреждении загруженных данных терминал отбрасывает их и запрашивает повторно
- если обновление затрагивает несколько компонентов и один из них не обновился, терминал фиксирует частичное обновление и продолжает попытки для оставшихся компонентов
- все ошибки записываются в локальный журнал для последующей диагностики

## 6. Требования к безопасности

- аутентификация терминалов при обращении к центральному репозиторию
- контроль целостности передаваемых данных
- журналирование операций: публикация, доставка, применение, откат
- отчёты терминалов не содержат персональных данных и конфиденциальной информации
